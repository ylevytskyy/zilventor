# P9 — Close R2 fully (machining-preset coverage)

Branch: `feat/p9-preset-coverage`. Not part of the original P1–P8 ABF-parity program (`docs/superpowers/plans/2026-07-02-abf-parity-milestones.md`, marked "PARITY PLAN COMPLETE" at P8) — P9 is a follow-up opened to close the gap P3 itself flagged and left open (scope call S2 in `docs/superpowers/plans/2026-07-02-p3-machining-presets-cam-metadata.md`: *"MVP apply-preset UI = bores only via BorePropertiesPanel; groove model-level fields flow through export but have no UI. Creation-command wiring (hinge/shelfpin/tandem/…) explicitly deferred as follow-up."*). ADR: `docs/adr/0001-machining-presets-global-with-snapshot.md` (accepted — presets are app-global, snapshot-on-apply, never live-linked).

## Goal

R2 ("machining presets") reads `partial` in `docs/abf-plugin/05-parity/03-processing-parity-requirements.md`, but the text describing what's missing is stale — it predates P3 shipping. The actual remaining gap, verified against code, is narrower than the doc implies:

1. Presets can only be applied **after** a bore already exists, one at a time, via `BorePropertiesPanel`. No hardware-creation command (drawer bank, leg levelers, shelf-pin) lets the user pick a preset while creating the hardware.
2. Grooves have **zero** properties-panel UI. `GrooveSpec` already carries `toolNumber`/`speed`/`presetLayerName` (added in P3), but nothing in the app lets a user set them — only a test could.
3. The `machining.csv` sidecar ships only in the per-material-folders ZIP export; the combined single-DXF export mode has no CSV, only inline XDATA.

Plus: the requirements doc's R2 section and R7 traceability row are wrong and need updating regardless of what else lands.

## Context (verified against code, not the requirements doc's prose)

- **`MachiningPreset` type** — `packages/shared/src/machiningPreset.ts`: `{ id, name, opType: BoreRole | 'groove' | 'tenon' | 'mortise', diameter, depth, offset?, layerName, toolNumber?, speed? }`. Also exports `validateMachiningPresetImport`, `serializeMachiningPresets`.
- **Storage** — `packages/app/src/store/useAppStore.ts`: `readMachiningPresetsFromStorage()` / `persistMachiningPresets()` (localStorage key `machiningPresets`, ~lines 18/30); store fields `machiningPresets`, `addMachiningPreset`, `updateMachiningPreset`, `deleteMachiningPreset`, `importMachiningPresets`, `machiningPresetsDialogOpen`/`toggleMachiningPresetsDialog` (~lines 462-468, 892, 938-959).
- **Apply-to-bore command** — `packages/app/src/commands/ApplyMachiningPresetCommand.ts`: constructor `{ bore: BoreOp; values: MachiningPresetValues; partPath: string; doc: { bores?: BoreOp[] }; opfs: OpfsRW | null }` where `MachiningPresetValues = { diameter; depth; layerName; toolNumber?; speed? }`. **Takes snapshotted values, not a preset id** — deliberate decoupling per ADR 0001 (editing a preset later must never retroactively change an applied bore). `apply()` mutates `bore.diameter/depth/presetLayerName/toolNumber/speed`, `revert()` restores prior state exactly (including field absence). This is the pattern every new apply-command in this milestone must mirror.
- **`BorePropertiesPanel`** — `packages/app/src/shell/BorePropertiesPanel.tsx` (355 lines). Its own, **separate** selection channel: `s.selectedBoreId` + `s.selectedBorePartPath` (not `s.selectedFeatureId`). Resolves the live bore via `getLiveBores(partPath)`, returns `null` if nothing selected, filters `machiningPresets` by `p.opType === bore.role`. Mounted as a sibling of the generic `<PropertiesPanel />` in `packages/app/src/App.tsx` (~line 5555-5560) — both subscribe independently to store state; there is no shared dispatch switch.
- **`PropertiesPanel.tsx`** (`packages/app/src/shell/PropertiesPanel.tsx`, 50 lines) reads `s.selectedFeatureId`, looks the feature up in `activePart.featureTree`, and only produces real content when `feature?.kind === 'extrude'`. Any other kind — including `'groove'` — falls through to the generic empty-state placeholder (`t('panel.properties.selectFeature')`), visually indistinguishable from "nothing selected." Confirmed no groove-specific branch exists.
- **`GrooveFeature`** — `packages/shared/src/groove.ts:15-32`. `GrooveSpec` already has `toolNumber?`, `speed?`, `presetLayerName?` (P3 added these to the model; only the UI is missing). `grep -rl GroovePropertiesPanel packages/` returns nothing — confirmed the file doesn't exist anywhere.
- **No groove selection surface exists at all** (verifier-confirmed, file:line): zero groove references in `SceneManager.ts`/`Viewport.tsx` — no 3D raycast marker to click a groove. `BrowserPane.tsx:453-640` has no `kind==='groove'` branch; grooves fall through to a mislabeled `▸ ExtrusionN` tree node wired only to `setSelectedFeature`. A `GroovePropertiesPanel` alone (as originally scoped in W1) would ship with nothing able to trigger it — W1 must include the selection wiring itself, not just the panel. Store precedent test to mirror: `useAppStore.selectedBore.spec.ts` (not the generic `useAppStore.spec.ts`).
- **Bore preset-apply bypasses the command bus** (verifier-confirmed): `BorePropertiesPanel.tsx` calls `ApplyMachiningPresetCommand`'s `.apply()` directly, not `bus.execute()` — so applying a preset to a bore today is **not undoable** and doesn't appear in the undo stack. Pre-existing gap, not part of R2's disclosed scope; P9 must decide whether the new groove path repeats it or fixes it going forward (see D8).
- **Hardware-creation commands** (none currently accept a preset id or snapshotted values):
  - `AddDrawerBankCommand` (`packages/app/src/commands/AddDrawerBankCommand.ts`) — `slideSystem?: 'sideMount' | 'tandem'` (line 73); when tandem, generates bores of **two** distinct `opType`s (`tandem-cabinet` and `tandem-drawer-bottom`/`tandem-drawer-back`). Dialog: `packages/app/src/shell/DrawerBankDialog.tsx`.
  - `AddLegLevelersCommand` (`packages/app/src/commands/AddLegLevelersCommand.ts`) — single opType `legLeveler`. Dialog: `packages/app/src/shell/LegLevelersDialog.tsx`.
  - Shelf-pin / System-32: `GenerateShelfPinBoresCommand.ts` + `AddManualShelfPinBoresCommand.ts` + `UpdateShelfPinStartOffsetCommand.ts`, dialog `ShelfPinDialog.tsx` — single opType `shelfPin-system32`.
  - Hinges have **no standalone command** — hinge-cup and hinge-plate bores are generated inside `AddDoorCommand.ts` (`hingeCupBores`, `hingePositions`, `hingePlateBores`), driven by `panel.doorSpec` fields on the door dialog (not investigated in depth this round). Two distinct opTypes (`hingeCup`, `hingePlate`) entangled with door creation.
  - `EditBoreCommand.ts` is the closest existing "mutate an existing BoreOp in place" pattern (the one `ApplyMachiningPresetCommand`'s own plan doc says it mirrors).
- **CSV sidecar** — `packages/app/src/drawing/manufacturingCsv.ts`: `buildManufacturingCsv(inputs: PanelManufacturingInput[]): string`. Called from `packages/app/src/commands/ExportPanelManufacturingDxfCommand.ts` inside the `!combined` (folders/ZIP) branch only (~lines 77-91: `const combined = this.opts.mode === 'combined'`). The combined branch produces a raw single `Uint8Array` `.dxf` — not a zip — with no CSV; XDATA is the only CAM metadata carried in that mode today.
- **Requirements doc** — `docs/abf-plugin/05-parity/03-processing-parity-requirements.md`, R2 section, currently says (paraphrased): *"Missing: (a) toolNumber/speed fields anywhere in the model — nothing carries CAM tool-assignment data; (b) no user-configurable layer naming; (c) no preset concept at all."* All three are now false — `toolNumber`/`speed` exist on `BoreOp`/`GrooveSpec`, `presetLayerName` is presettable, and the full `MachiningPreset` CRUD system exists. The R7 traceability table's R2 row (`status: partial`) is stale for the same reason.
- **Manifest**: `CURRENT_FORMAT_VERSION = 39` (`packages/shared/src/fileFormat.ts:4`). Presets are app-global localStorage (ADR 0001), not manifest fields. `BoreOp`/`GrooveSpec` already have `toolNumber`/`speed`/`presetLayerName` from P3 — no new manifest fields are anticipated by this milestone (see Decision D5 below).
- **Test commands** (per-package, never root vitest): `packages/{app,shared,kernel}` each have `pnpm --filter <pkg> typecheck` (`tsc --noEmit`) and `pnpm --filter <pkg> test:unit` (`vitest run`); kernel additionally has `test:integration` (`vitest run --config vitest.integration.config.ts`). E2E: `playwright test --project=chromium` (`testDir: ./tests/e2e`).

## Decision log (scope calls)

- **D1 — Preset-picker payload shape at creation time.** Dialogs resolve the chosen preset from the store and pass **snapshotted values** (not a `presetId`) into the command's params, mirroring `ApplyMachiningPresetCommand`'s existing decoupling (ADR 0001: editing a preset later must not retroactively change already-created hardware). Recommended. Confidence: 80.
- **D2 — Which hardware-creation commands get a picker in P9.** Slice per command, in order of opType simplicity: shelf-pin (`shelfPin-system32`, 1 opType) → leg-levelers (`legLeveler`, 1 opType) → drawer-bank tandem (`tandem-cabinet` + `tandem-drawer-bottom`/`-back`, 2 opTypes, needs 2 dropdowns). **Hinges deferred out of scope** — `AddDoorCommand`'s hinge-bore generation and its dialog weren't investigated this round, and folding an under-researched command into this milestone risks scope creep; better as a fast P10 follow-up once actually explored. Recommended. Confidence: 70 (the shelf-pin/leg-leveler/drawer-bank ordering is solid; deferring hinges is the debatable part — flag for user review).
- **D3 — GroovePropertiesPanel selection routing.** New, independent selection channel (`selectedGrooveId` + `selectedGroovePartPath` in `useAppStore`), mirroring `BorePropertiesPanel`'s own established pattern — not a new branch inside the generic `PropertiesPanel.tsx`'s `feature.kind` switch. Keeps the change surgical (no risk to the existing `'extrude'` path) and matches precedent already in this codebase. Recommended. Confidence: 70.
- **D3b — Groove selection *trigger* (new, verifier-surfaced).** Since no groove selection surface exists at all (see Context), decide how the user actually selects a groove to open the new panel: (a) **browser-tree only** — add a `kind==='groove'` branch in `BrowserPane.tsx` (replacing the mislabeled `▸ ExtrusionN` fallback) that sets `selectedGrooveId`, no 3D pick; (b) **browser-tree + 3D raycast marker** — additionally add a groove hit-target in `SceneManager.ts`/`Viewport.tsx` mirroring however bores are made pickable in 3D. Recommended: **(a) browser-tree only for P9**, deferring the 3D raycast marker — it's a materially bigger, higher-risk change (new geometry/raycasting code) for a UI convenience that isn't required to unblock preset application, and BorePropertiesPanel's own bores are reachable via 3D pick today but grooves have no precedent to mirror cheaply. Confidence: 65 — reasonable default, but a 3D-pick-only user would find grooves unreachable; flag for user review if 3D selection is expected UX parity with bores.
- **D4 — Groove apply command implementation (REVISED — user AFK, provisional; orchestrator+verifier converged).** Widen the existing `ApplyMachiningPresetCommand` (`ApplyMachiningPresetCommand.ts:20-26,59-91` is pure field-copying) to accept a discriminated target — e.g. `{ kind: 'bore'; bore: BoreOp } | { kind: 'groove'; groove: GrooveFeature }` — instead of a new parallel file. `GrooveSpec` (`groove.ts:15-32`) already carries optional `toolNumber?/speed?/presetLayerName?` anticipating exactly this. The groove branch must still enforce the field-transfer restriction from the original call: only `toolNumber`/`speed`/`presetLayerName` ever get written for a groove target — `diameter`/`depth`/`width` are never touched. Supersedes the original D4 ("new `ApplyMachiningPresetToGrooveCommand` file"). Confidence: 70 (widening is the right call given the command is already pure field-copying and the model anticipates it; residual risk is keeping the two branches' field-transfer rules from leaking into each other — cover with a dedicated test per branch).
- **D5 — No manifest bump.** All fields written by D1–D4 (`toolNumber`, `speed`, `presetLayerName`) already exist on `BoreOp`/`GrooveSpec` since P3; nothing new is added to the manifest schema. `CURRENT_FORMAT_VERSION` stays at 39. Recommended, high confidence: 90.
- **D6 — Combined-mode CSV sidecar container (RESOLVED — user AFK, provisional; orchestrator+verifier converged).** Original zip-of-two option is **rejected**: it breaks 4 existing test contracts — `tests/e2e/drawing/manufacturing-dxf.spec.ts:242-245` (asserts no PK/zip signature on combined output) and `:254-256` (asserts `.dxf` filename), `ExportPanelManufacturingDxfCommand.spec.ts:162` and `:220-234` (asserts combined output is byte-for-byte unaffected, no CSV) — plus the source comment at `ExportPanelManufacturingDxfCommand.ts:78-80` records combined-untouched as a deliberate prior decision, not an oversight. **Resolved to: two sequential downloads** — the combined `.dxf` download stays byte-for-byte unchanged (primary artifact, no format/extension change), and `machining.csv` is triggered as a second, separate browser download from the same button click. Open sub-decision: whether the second download fires unconditionally or only when the export inputs actually carry machining metadata (any bore/groove with a non-empty preset-derived field) — recommend **only when metadata exists**, to avoid a useless empty CSV landing in Downloads on every combined export. Confidence: 70 for "two sequential downloads" (directly resolves the test-contract conflict); 60 for the "only when metadata exists" gating (reasonable default, not verified against existing UX conventions elsewhere in the app). The one test that **must** change regardless: `ExportPanelManufacturingDxfCommand.spec.ts:220-234`'s "no CSV in combined mode" assertion is now a deliberate contract update, not a regression — call this out explicitly in the PR/commit, not just in this doc.
- **D7 — Nest-export CSV parity.** Not investigated this round (`ExportNestDxfCommand.ts` / `renderNestSheetDxf.ts` / `renderCombinedNestDxf` — unconfirmed whether folders-mode nest export has its own CSV sidecar). Out of scope for P9; the user's disclosed gap was specifically the panel-manufacturing export. Flagging as an open question for a future milestone, not silently dropping it. Confidence: 80 (that it's fine to defer, not that nest export definitely lacks parity).
- **D8 — Command-bus bypass disclosure (new, verifier-surfaced).** The existing bore preset-apply path calls `.apply()` directly, not `bus.execute()` — pre-existing gap, undoable-in-name-only. Decision: the **new groove apply path goes through `bus.execute()`** (correct, undoable) while the **existing bore path is left as-is** — fixing it is out of scope for P9 (surgical-change principle: don't repair adjacent pre-existing bugs the user didn't ask about). This does mean bore-apply and groove-apply will behave inconsistently (one undoable, one not) until a future cleanup. Recommended, orchestrator pick. Confidence: 65 — the "don't fix bore in P9" half is solid (90, matches CLAUDE.md §3 surgical-changes); the "leave a known inconsistency between two nearly-identical features" half is the debatable part or the user may prefer both bypass or both go through the bus for consistency — flag for user review.
