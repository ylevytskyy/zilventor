# P10 — R1 hardening (preflight guardrails made real)

Branch: `feat/p10-r1-hardening`. Follow-up to the ABF-parity program (P1–P8, `docs/superpowers/plans/2026-07-02-abf-parity-milestones.md`, "PARITY PLAN COMPLETE"), in the same vein as P9 — closing a gap R1 itself flagged as future work. `docs/abf-plugin/05-parity/03-processing-parity-requirements.md` R1 status (line 25, just re-synced, accurate) reads: *"`isManifold` is a caller-supplied extension point (stub), not wired to a live geometry check — closing it is planned for a future milestone (P10)"* and *"the `split-required` branch is not reachable in practice today — every call site passes `solidCount: 1`."* This plan closes both.

## Goal

`panelPreflight(part)` in `@zilventor/shared` (`packages/shared/src/panel-preflight.ts:45-59`) already implements the full `pass | split-required | fail` contract and is genuinely wired into its call sites — but two of its three branches are currently unreachable in production because the values feeding it are lies of convenience, not measurements:

1. **`isManifold` is never set.** Confirmed by repo-wide grep: every production call site omits the field entirely (defaults to `undefined`, treated as "assumed valid"). No OCCT validity/manifold check exists anywhere in `packages/kernel/src` today, even though `opencascade.js` (the WASM binding already vendored) exposes exactly what's needed (`BRepCheck_Analyzer`, `ShapeAnalysis_Shell`).
2. **`solidCount` is always the literal `1`,** even for imported STEP parts that may carry 2+ solids in one `ImportedFeature`. Both call sites hardcode it; the field that would make it truthful (`ImportedFeature.solidColors.length`) already exists and is already persisted in the manifest — it's just never read for this purpose.

The fix is **not** a STEP-import redesign. It's: compute a real manifold flag once (at import/explode time, where the shape is already loaded in OCCT), persist it exactly like `solidColors` already is, and read both real fields at the one existing choke point (`resolvePanelSpec.ts`) that already feeds both the boring and the cut-list/DXF/nesting pipelines.

## Context (verified against code)

- **`panelPreflight`** (`packages/shared/src/panel-preflight.ts:45-59`) — pure, synchronous, no kernel/OPFS access (file header, lines 4-13, states this explicitly by design). Input `PanelPreflightInput` (`:16-27`): `{ name, materialId, solidCount: number, isManifold?: boolean }`. Return `PanelPreflightResult` (`:29-32`): `{kind:'pass'} | {kind:'split-required', reasonKey, solidCount} | {kind:'fail', reasonKey}`. Branch order matters: `solidCount > 1` is checked **before** the manifold/name/material checks, so a caller can trigger `split-required` while passing an arbitrary/undefined `materialId` — useful below (§W4).
- **Two production call sites, both hardcode the stub values:**
  - `packages/app/src/shell/resolvePanelSpec.ts:43` — `panelPreflight({ name: manifest?.document?.name, materialId: spec.materialId, solidCount: 1 })`. This function only ever reaches that line when it already found a `PanelFeature` in the tree (`resolvePanelSpec.ts:31-34`: `if (!panel) { cache.set(partPath, null); return null; }` — **silent early return, no preflight call, no diagnostic**, for any part without a `PanelFeature`, including all imported STEP parts). Since a `PanelFeature` box is always exactly one kernel-built solid, `solidCount: 1` is provably correct *for this branch* — the bug is that imported parts never reach the preflight call at all today, so `split-required` can't fire for them regardless of what `solidCount` says.
  - `packages/app/src/assembly/walkers/aggregateBoresRecursive.ts:54` — `panelPreflight({ name: partName, materialId: spec?.materialId, solidCount: 1 })`. This walker does **not** gate on `spec === null` (only reads `spec?.materialId`), so it's the one place an imported part could in principle still hit `panelPreflight` — but it only has access to a pre-built `panelSpecs: Map<string, PanelSpec|null>`, not the raw `featureTree`, so it can't compute a real `solidCount`/`isManifold` on its own.
- **Both call sites share one cache.** `useBoringResult.ts:12,27-33` and the cut-list path both read `panelSpecCacheRef` from `CutListCacheContext`, populated by the same `resolvePanelSpec()` calls (`loadCutListInputs.ts:16`: `resolvePanelSpec(opfs, p, cache, diagnostics)`). **This means `resolvePanelSpec.ts` is the single choke point feeding both the boring diagnostic path and the manufacturing-DXF/nesting diagnostic path** — fixing it there fixes both consumers without touching `aggregateBoresRecursive.ts` or `aggregateCutListRecursive.ts`. (Nesting doesn't call `panelPreflight` itself; `OpenNestingTabCommand.ts:7,14` only consumes an already-collected `diagnostics` array threaded up from the same `resolvePanelSpec`/`loadCutListInputs` pipeline — confirmed no separate wiring needed.)
- **`ImportedFeature`** (`packages/shared/src/types.ts:60-78`) — `{ kind:'imported', id, sourceStep, bodyRef, color?, solidColors?: (string|null)[] }`. `solidColors` (added by the per-body-color milestone, commit `133271ad`) is index-aligned with OCCT's `TopExp_Explorer_2(shape, TopAbs_SOLID, TopAbs_SHAPE)` enumeration — its `.length` is already the true solid count, no kernel round-trip needed to read it. `panel-preflight.ts:11-13`'s own docstring already anticipates this exact sourcing. No `isManifold` field exists yet on this type — needs to be added, optional, mirroring `solidColors`.
- **`{ kind: 'imported', ... }` is constructed in four places, not two.** Verifier-confirmed: besides `buildImportedPartDocument` (used by `importStepIntoNewPart(s)`) and `ExplodeIntoAssemblyCommand`, `InventorImporter.ts:194-197` constructs an `ImportedFeature` **inline**, bypassing `buildImportedPartDocument` entirely — and it's a live, wired path: `App.tsx:512` → `ImportFromInventorCommand.ts` → `runInventorImport`. All four sites must gain `isManifold` in W3, or Inventor-imported parts keep the stub `isManifold === undefined` (soft-pass) behavior forever, silently defeating this milestone for that import path.
- **Hard invariant: `isManifold: false` must survive optional-field spreading, not be dropped by a truthy-spread idiom.** `tsconfig.base.json:10` sets `exactOptionalPropertyTypes: true`, and the existing precedent for optional `ImportedFeature` fields — `buildImportedPartDocument.ts:29-30`, `...(color ? { color } : {})` — spreads on **truthiness**, which would silently omit `isManifold: false` (the one value that actually matters) if copied verbatim. Every one of the four construction sites (W3) must gate on `!== undefined`, e.g. `...(isManifold !== undefined ? { isManifold } : {})`, never on truthiness. Getting this wrong recreates, byte-for-byte, the exact silent-lie failure mode this milestone exists to fix.
- **No manifold-check API exists in the kernel.** Grep of `packages/kernel/src` for `BRepCheck_Analyzer|ShapeAnalysis|IsValid|manifold|closed|watertight` finds only unrelated hits (`SweepOps.ts` wire-closed checks, `MANIFOLD_SOLID_BREP` as a STEP entity-name string in a comment). `opencascade.js` (`packages/kernel/package.json`: `"opencascade.js": "2.0.0-beta.b5ff984"`) **does** expose what's needed, unused today: `BRepCheck_Analyzer` (`constructor(shape, GeomControls, theIsParallel)`, `.IsValid_1/_2()`) and `ShapeAnalysis_Shell` (`.HasFreeEdges()`, `.FreeEdges()`, `.HasBadEdges()`). Existing kernel idiom for calling raw OCCT classes (`packages/kernel/src/occt/SolidOps.ts:24-34`): `new oc.ClassName_N(args)` → call → explicit `.delete()`.
- **Kernel↔app boundary is always async.** `packages/kernel/src/worker.ts` exposes the kernel via `Comlink.expose`; every one of `KernelApi`'s 40 methods returns a `Promise` (`grep -c '): Promise<' packages/kernel/src/api.ts` → 40). `kernel.importStep(...)` already returns `solidCount: number` transiently in its result (`packages/kernel/src/api.ts:131-145`) but doesn't persist it — the persisted, no-round-trip proxy is `ImportedFeature.solidColors?.length`, exactly as `panel-preflight.ts`'s docstring intends. This means **`panelPreflight` itself never needs to become async** — the only async work needed is at STEP-import/explode time (already async operations), computing and persisting `isManifold` once, the same way `solidColors` is already persisted once.
- **Multi-solid imports reach a single un-split `ImportedFeature` today.** `importStepIntoNewPart.ts:15-34` (part-mode STEP drop with no active assembly — `FileTab.tsx:228-242`, comment: *"Part-mode: import the whole compound shape... Use the Explode-into-Assembly command if individual bodies are needed"*) builds **one** `PartDocument` whose `ImportedFeature.bodyRef` is the whole multi-solid compound and `solidColors.length` already equals the true solid count. This is the exact scenario R1.1 targets and the one this plan makes `panelPreflight` see truthfully.
- **Perf precedent against a second full-shape pass.** `docs/superpowers/specs/2026-06-05-step-per-body-color-design.md:56-61` explicitly rejected re-parsing a STEP file a second time (`STEPCAFControl_Reader` after `STEPControl_Reader`) because it "contradicts the documented 171MB perf budget (~8.75 min) and a previously observed WASM heap leak from double-parsing." `BRepCheck_Analyzer` run once against the **already-loaded** shape (no re-parse) at the same import/explode call is not the same cost class as that rejected design, but running it with `GeomControls=true` (full geometric self-intersection checking, not just topology) on a very large compound is still an unmeasured cost — see D2.
- **i18n strings already exist for all four `panelPreflight` reason keys**, en + uk (`packages/app/src/i18n/locales/en.json:896-901`, `uk.json:896-901`): `missingMaterial`, `missingName`, `notManifold` ("...geometry is not a valid closed solid — cannot bore, nest, or export."), and — already present, not new — `splitRequired` ("Panel \"{{name}}\" contains {{solidCount}} solids — split it into separate parts before boring, nesting, or exporting."). No new locale strings are needed by this plan.
- **No runtime schema validator gates `ImportedFeature`'s shape** — `grep -n solidColors packages/shared/src/*.ts` shows it referenced only in the type definition and `panel-preflight.ts` comments, no zod-style parser to update. Adding `isManifold?: boolean` is a type-only, additive, optional change.
- **Manifest**: `CURRENT_FORMAT_VERSION = 39` (`packages/shared/src/fileFormat.ts:4`). Precedent (P9 D5): additive optional fields on existing types don't bump the version. `isManifold?: boolean` on `ImportedFeature` follows the same pattern — old manifests simply lack it, `undefined` already means "assumed valid" in `panelPreflight`'s own logic, so old files behave identically to today. **No manifest bump expected.**
- **Test commands** (per-package, never root vitest): `pnpm --filter {shared,kernel,app} typecheck` / `test:unit`; kernel additionally `test:integration` (real OCCT WASM). Baselines at master `b1d6b7c1`: tsc 0 ×5, shared 1450, kernel 306 unit + 372/373 integration, app 3555, build 0 (`pnpm -r build`), e2e 229/234 parallel (known-flaky CPU-contention allowance).

## Decision log (scope calls)

- **D1 — Keep `panelPreflight` synchronous; push the async work to import/explode time.** Rather than widening `panelPreflight` or its call sites to `Promise`-returning (which would ripple through `resolvePanelSpec`, `aggregateBoresRecursive`, `aggregateCutListRecursive` — all currently sync/already-async-elsewhere in ways that don't need a new kernel round-trip per call), compute `isManifold` **once**, at STEP import/explode time (already async, already the place `solidColors` gets computed), and persist it on `ImportedFeature` exactly like `solidColors`. `panelPreflight` and both its call sites stay untouched in shape — only the *values* they read become truthful. Recommended. Confidence: 85.
- **D2 — Manifold check scope: imported parts only, computed once, topology-only rigor by default.** Run the check only for `ImportedFeature`-sourced shapes (never for `PanelFeature` boxes — those are manifold by kernel construction, per the existing code comment at `resolvePanelSpec.ts:41-42`, and running `BRepCheck_Analyzer` on every parametric export would be pure waste with zero diagnostic value). Run it once, at `kernel.importStep`/`kernel.splitImportedShape` time, against the already-loaded shape — not a second parse. Default to `BRepCheck_Analyzer(shape, GeomControls=false, parallel=false)` (topology-only: closed/free-edge checks) rather than `GeomControls=true` (adds full geometric self-intersection analysis) to bound worst-case cost on large compounds. **Recommended. Confidence: 68** (raised from an earlier 55 pass). Reasoning: the `(shape, GeomControls, theIsParallel)` constructor signature is confirmed directly in the bundled, untrimmed type surface (`opencascade.full.d.ts:122971-122978`; `ShapeAnalysis_Shell` at `:166120`), so the topology-only call is a real, low-risk API — not speculative. The 171MB-import-tolerated precedent covers the "does this hang the UI" risk (it's async, off the main thread, same as today). What it does **not** cover: the kernel worker is single-threaded, so the analyzer call serializes against any other queued kernel calls, adding real (if bounded) wall-time to the critical import path — unmeasured. Residual risk is cost, not correctness or feasibility, hence the confidence bump; a perf smoke test is added as an explicit gate item (see Gate) rather than left as an open question.
- **D3 — UI on fail/split-required: reuse existing i18n strings, no new locale work; no clickable remediation action in P10, but only as a scope narrowing, not a capability gap.** `panel.preflight.notManifold` and `panel.preflight.splitRequired` already exist in en/uk and already read as actionable guidance. **Correction to an earlier draft of this doc:** the claim that action-button support was unconfirmed was wrong — `showToast(message, action?: { label, fn })` **already supports action buttons** (`App.tsx:289`, `:418-424`, `:5862-5870`), with a live remediation precedent already shipped: `App.tsx:2138-2144` wires a "show conflict" action onto an over-defined-dimension toast. So a clickable "Explode into Assembly" action is not blocked by missing infrastructure. **Resolution (orchestrator call, user AFK): still keep P10 scoped to no action button**, because wiring one correctly needs per-entry-point part-path context — the `split-required` toast fires from three different call sites (boring/DXF/nesting tabs), each needing to resolve and pass the *correct* `partPath` into `ExplodeIntoAssemblyCommand`'s dispatch, which is itself a small, clean, well-understood follow-up now that the precedent is confirmed rather than an open research question. Recommended, confidence 70 (moderate-high: the technical path is now clear, the only real judgment call is sequencing it as a fast P10.1 follow-up rather than folding it in now).
- **D4 — No manifest version bump.** `isManifold?: boolean` on `ImportedFeature` is additive/optional; absent = `undefined` = today's existing "assumed valid" default in `panelPreflight`. `CURRENT_FORMAT_VERSION` stays 39. Recommended, high confidence: 88.
- **D5 — Single choke point: fix `resolvePanelSpec.ts`, not `aggregateBoresRecursive.ts`/`aggregateCutListRecursive.ts`.** Both boring and cut-list/DXF/nesting consumers already share one `panelSpecCacheRef`/`resolvePanelSpec` pipeline (see Context). Add the imported-part branch inside `resolvePanelSpec.ts` once; both downstream walkers get truthful diagnostics for free via the existing `diagnostics` threading, with zero changes to either walker file. Recommended, confidence 80 — the shared-cache fact is directly confirmed in code, not inferred.
- **D6 — Test strategy split by layer.** The `BRepCheck_Analyzer` wrapper (needs real OCCT WASM, needs an actual watertight-vs-broken shape fixture) belongs in kernel `test:integration`, mirroring `StepIO`'s existing integration-test style, not `test:unit`. The `resolvePanelSpec`/`ImportedFeature`-construction wiring belongs in app `test:unit` with a mocked kernel client result (existing app-test convention — app unit tests never load real WASM). Recommended, confidence 70.
- **D7 — Solid-level granularity: whichever shape ends up as `ImportedFeature.bodyRef` gets its own `isManifold`.** Both `kernel.importStep` (whole-compound case) and `kernel.splitImportedShape` (per-solid case, used by `ExplodeIntoAssemblyCommand` and `importStepIntoNewParts.ts`) compute/return `isManifold` for the exact shape they're returning, not just the top-level compound — so a post-explode single-solid `ImportedFeature` gets an accurate per-solid flag, not a stale compound-level one. Recommended, confidence 75.

## Out of scope

- STEP-import redesign, auto-split-on-import, or any change to `importStepIntoNewPart`'s "whole compound as one Part" default behavior — R1.1 requires the diagnostic to fire truthfully, not that the system auto-splits.
- A clickable "Explode into Assembly" remediation action wired to the `split-required` toast — deferred per D3 as a deliberate scope narrowing, **not** because the capability is missing: `showToast` already supports actions (`App.tsx:289,418-424,5862-5870`, precedent at `App.tsx:2138-2144`). Deferred because wiring it correctly needs per-entry-point `partPath` context (boring/DXF/nesting toasts fire from different tabs) — flagged as a fast, well-scoped P10.1 follow-up now that the precedent is confirmed.
- `GeomControls=true` (full geometric self-intersection analysis) in the manifold check — deferred per D2 to a topology-only default; upgrading is a follow-up once perf is measured.
- Any UI surface for a user to manually mark/override `isManifold` on an already-imported part.
- Extending `panelPreflight` or any call site to be `async` — deliberately avoided per D1.
- Re-deriving `isManifold` for parts imported *before* this milestone shipped (no backfill/migration) — old manifests simply read as `isManifold: undefined` (assumed valid), identical to today's behavior; consistent with D4's no-bump decision.
