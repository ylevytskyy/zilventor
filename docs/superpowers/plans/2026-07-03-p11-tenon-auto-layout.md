# P11 — auto-spaced multi-tenon layout

Branch: `feat/p11-tenon-auto-layout`. Follow-up to P6 mortise/tenon joinery (`docs/superpowers/plans/2026-07-02-p6-mortise-tenon.md`), closing the stretch item P6's own S3 explicitly deferred: *"'Auto-matching' = manual tenon params, auto-derived mortise face/position/axis. NOT full auto-layout along the joint line (stretch, later)."* (P6 plan, line 23). This plan is "later."

## Goal

Today `TenonMortiseDialog` requires the user to hand-enter `count` and `spacing` (mm) and hand-compute whether `N` tenons of `width` mm actually fit within the picked joint's edge length — there is no feedback until the geometry is built. P11 adds an **auto-layout mode**: the user picks the two panels as today, then chooses `count` (I want N tenons) or `pitch` (target spacing ~P mm), and the system derives `count`/`spacing` from the joint's real edge length, centered, with end margins so tenons aren't flush to the panel edge. Manual mode stays available and remains the default-compatible path.

## Context (verified against code)

- **`TenonMortiseParams`** (`packages/shared/src/tenonMortiseMath.ts:118`) = `{width, depth, count, spacing, fitClearance, position?}` — all plain numbers, no derived/lazy fields. `position` (the center of the tenon group along the joint's run axis) defaults to `jointLength(joint)/2` when omitted (`tenonMortiseMath.ts:173`).
- **`jointLength(j: JointInput): number`** (`tenonMortiseMath.ts:137-140`) — `Math.hypot` of `joint.line.p0`/`p1`. **Private, module-local, not exported** — its own comment notes it mirrors an equally-private one-liner already in `connectorCatalog.ts`. This is the only place joint edge length is computed today, and only to default a single scalar (`position`), never to drive a count/spacing derivation.
- **`generateTenonMortisePair(joint, params, ids)`** (`tenonMortiseMath.ts:168`) computes `jointLength` internally, defaults `position`, then calls `buildTenonMortiseCutters(panelDims, spec)` per side. `buildTenonMortiseCutters` places tenon `i` at `spec.position + (i - (count-1)/2) * spec.spacing` — i.e. **evenly-centered multi-tenon spacing already exists** as a mechanism; the gap is purely that `count`/`spacing` must be supplied as literals today instead of derived from the edge length.
- **`AddTenonMortiseCommand`** (`packages/app/src/commands/AddTenonMortiseCommand.ts`) loads both panels' dims, calls `inferManualJoint(a.input, b.input)` (`packages/shared/src/jointMath.ts:82`) → `Joint | null`, then `generateTenonMortisePair`. If the picks don't form a butt joint, `inferManualJoint` returns `null` and the command **silently no-ops** (`AddTenonMortiseCommand.ts:108`, comment `// not a butt joint → no-op`) — no thrown error. `FurnitureTab.tsx` (`handleAddTenonMortise`, line 465-497) detects the no-op by diffing `featureTree.length` before/after and shows toast `toast.tenonMortiseNoJoint`. This is the only rejection precedent for this command; `EditRejectedError` (`EditPlacedPanelCommand.ts:10-14`, throw-based) is a *different* command's convention and not used here.
- **No exported joint-length/span utility exists anywhere** in `packages/shared` — `jointLength` in `tenonMortiseMath.ts` and a near-duplicate private one-liner in `connectorCatalog.ts` are the only two computations, both private.
- **Kernel regeneration only ever sees literal params.** Nothing found in the kernel fuse/cut branches (or anywhere else) that re-derives `count`/`spacing` from panel geometry on tree re-execute — `buildTenonMortiseCutters` takes `panelDims` + a `TenonMortiseSpec` of literal numbers. This means **auto-layout must resolve to concrete numbers once, at Add-time**, in `generateTenonMortisePair`/`AddTenonMortiseCommand` — never inside the kernel's regen path — or the kernel branch would need new logic to understand a `layout` descriptor, which nothing today expects.
- **No edit/regenerate command exists for `TenonMortiseFeature`** (unlike nesting's `EditPlacedPanelCommand`). Research found no `EditTenonMortiseCommand` anywhere. If this is wrong, the "auto-ness is not retained after creation" tradeoff below is less safe than assumed — flagged in Decision log D1.
- **`TenonMortiseDialog`** (`packages/app/src/shell/TenonMortiseDialog.tsx`, 127 lines) — fields width/depth/count/spacing/fitClearance/position, `Number(...)` coercion only, no validation. i18n keys under `dialog.tenonMortise.*` in `packages/app/src/i18n/locales/{en,uk}.json` (line 716 block): `title` "Tenon/Mortise"/"Шип/Гніздо", `width`/`depth`/`count`/`spacing`/`fitClearance`/`position` each with UA translations already in place (`Ширина (мм)`, `Крок (мм)`, etc.) — naming pattern `dialog.tenonMortise.<field>` is the one to extend. Toast key pattern: `toast.<featureCamelCase><Reason>`, e.g. existing `toast.tenonMortiseNoJoint`.
- **`FurnitureTab.handleAddTenonMortise`** chains two `viewport.beginOneComponentPick(...)` calls (panelPathA, panelPathB) then opens the dialog. The dialog does **not** have panel dims/joint geometry available at open time — it only receives `panelPathA`/`panelPathB`. Auto-layout's live preview (and the resolve-before-submit step) needs `jointLength`, so it must be computed by `FurnitureTab` (which can load panel dims + call `inferManualJoint`, exactly as `AddTenonMortiseCommand` does) and passed into the dialog as a prop. This duplicates a cheap, pure computation the command re-does anyway — acceptable (Decision log D4).
- **ABF's own joinery UX doesn't cover this.** `docs/abf-plugin/03-machining/02-hardware-boring-and-joinery.md` (lines 51-94, "Mark Intersection") describes a single-pocket, double-click, intersection-driven marker for one male/female panel pair — not an evenly-spaced N-tenon layout along an edge. There is no ABF precedent to mirror; this is a net-new capability beyond ABF parity, not a gap-closing one.
- **Manifest**: `CURRENT_FORMAT_VERSION = 39` (`packages/shared/src/fileFormat.ts:4`; P7/P8 bumped past P6's v37). Per the P9/P10 precedent (additive optional fields on existing types don't require a version bump — P10 D4, confidence 88), and because this plan's design (below) resolves auto-layout to literal `count`/`spacing`/`position` **before** the `TenonMortiseFeature` is constructed, **the persisted feature shape doesn't change at all** — not even an additive optional field. **No manifest bump expected.**
- **Baselines** (master, per current session state — re-confirm at gate time, not blindly, per P10's own convention): tsc 0 ×5, shared 1451, kernel 306 unit + 376/377 integration, app 3574, build 0 (`pnpm -r build`), e2e 231/234 parallel (known-flaky CPU-contention allowance).

## Decision log (scope calls)

- **D1 — Resolve auto-layout to literal numbers once, at Add-time; do not persist a `layout` descriptor on `TenonMortiseFeature`.** Since kernel regeneration only ever consumes literal `count`/`spacing`/`position` (Context, "Kernel regeneration only ever sees literal params"), and no edit/regenerate command exists for this feature kind, there is nothing today that would re-run an auto-layout on a later panel resize even if we persisted the intent — persisting `layout` would add schema surface with no consumer. Compute `count`/`spacing` via a new pure function inside `generateTenonMortisePair`'s resolution step (or a thin wrapper called by `AddTenonMortiseCommand` before it), store the resolved literals exactly as manual mode does today. **Recommended. Confidence: 78.** Self-critique: if an edit/regenerate command for tenon/mortise ships later (plausible — nesting already has one), this design silently loses "this was auto-derived" provenance, forcing that future work to either re-derive from scratch or accept manual-only edits. Low near-term cost given no such command exists today; flagging so a future planner doesn't assume auto-ness is recoverable.
- **D2 — Support both `count` and `pitch` auto-layout modes.** `mode: 'count'` (user wants exactly N tenons) and `mode: 'pitch'` (user wants ~P mm spacing, count derived) both have real joinery use cases — count is the simpler mental model for casework, pitch matches shop-floor "roughly every 32mm" conventions already used elsewhere in the app (System-32 spacing). Implementing both in one function (`layoutTenonsAlongJoint`) is marginal extra cost over one. **Recommended. Confidence: 70.**
- **D3 — End margin: fixed mm, user-overridable, defaulting to `width`.** Simplest rule that avoids a tenon sitting flush with the panel edge (weak short-grain corner) without inventing a new unit-less "fraction of pitch" concept the user has no precedent for elsewhere in the dialog. Default `minEndMargin = width` is a reasonable joinery rule of thumb, not verified against ABF (ABF doesn't cover this layout at all, per Context) or a woodworking spec — this is the plan's own judgment call. **Confidence: 55 (below the 60 review bar) — flag for user review**, specifically the default-equals-width choice; the mode/override mechanism itself is not in question.
- **D4 — `FurnitureTab` computes `jointLength` independently of `AddTenonMortiseCommand`, duplicating the `inferManualJoint` call, so the dialog can show a live auto-layout preview before submit.** Alternative (no live preview, resolve blind at submit and let the no-op/toast path catch total failures) was rejected — a silent "0 tenons fit" surprise after a full dialog fill-in is worse UX than the mild duplication of one cheap, pure, synchronous joint computation. Mirrors the existing precedent of `AddTenonMortiseCommand` itself re-deriving the joint fresh rather than caching it. **Recommended. Confidence: 72.**
- **D5 — Edge too short for the requested count: clamp to the largest feasible count (minimum 1, centered) and warn via toast, never throw/reject.** This command's own established convention for infeasible input is a silent-then-toasted UI signal (`toast.tenonMortiseNoJoint`), not `EditRejectedError`'s throw-based pattern (Context) — that pattern belongs to a different command (nesting edit) with a different UX (an in-progress drag the user can retry inline). Clamping preserves "the user gets *a* joint, imperfect but built" rather than a hard failure requiring dialog re-entry. Add a new toast key `toast.tenonMortiseClamped` (en/uk) mirroring the existing `tenonMortiseNoJoint` naming pattern. **Recommended. Confidence: 68.**
- **D6 — New pure function lives in `packages/shared/src/tenonMortiseMath.ts`, next to `jointLength`/`buildTenonMortiseCutters`, and is exported** (unlike the private `jointLength`) since both `AddTenonMortiseCommand` and `FurnitureTab` need to call it independently (D4). Signature: `layoutTenonsAlongJoint(jointLength: number, opts: {mode: 'count'|'pitch'; value: number; width: number; minEndMargin?: number}): {count: number; spacing: number; clamped: boolean}`. `position` is deliberately **not** part of the return — auto-layout is always centered, so the existing `position` default (`jointLength/2`) already does the right thing untouched. **Recommended. Confidence: 80.**

## Out of scope

- Any change to the kernel's tenon/mortise cutter branches — auto-layout resolves to literal params before the feature is constructed (D1), so the kernel never needs to understand a `layout` descriptor.
- An edit/regenerate command for `TenonMortiseFeature` that could re-run auto-layout after a panel resize — none exists today (Context); adding one is a separate milestone, not implied by this plan (flagged as a D1 self-critique risk, not built here).
- Heterogeneous tenon widths/spacing within one joint (all tenons in a group stay uniform width/depth, per the existing `TenonMortiseParams` shape).
- Curved or non-linear joints — `jointLength`/`inferManualJoint` only handle straight butt-joint lines today; out of scope to extend.
- Mirroring ABF's "Mark Intersection" double-click UX — ABF's mechanism is a different feature (single-pocket auto-marking on a second panel), not evenly-spaced N-tenon layout; not attempted here (Context).
- A manifest migration/version bump — explicitly not needed per D1/Context.
