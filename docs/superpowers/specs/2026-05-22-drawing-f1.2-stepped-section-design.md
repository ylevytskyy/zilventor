F1.2 is the third section-view variant. F1 introduced the single-plane kernel cut, ANSI heavy section line, label allocator, hatch generator, OPFS BREP cache, and stale-banner machinery. F1.1 extended `SectionView` (no new kind) with a `mode: 'full' | 'half'` flag and an oversized quarter-box second cut. F1.2 reuses everything F1 and F1.1 shipped — same projector pipeline, same label allocator, same cache, same Comlink worker, same stale banner — and extends the cutting strategy to a **polyline of axis-aligned segments** that bend across the part in 90° jogs.

## 2. Goal & non-goals

### 2.1 Done in F1.2

1. New `mode` value `'stepped'` on `SectionView` (extends the `'full' | 'half'` flag — NOT a discriminated union).
2. New optional field `stepSegments?: readonly StepSegment[]` on `SectionView`. Each segment is two 2D points in parent-view-local mm (pre-scale) space.
3. New `deriveStepPlanes(...)` helper in `packages/shared/src/drawing/sectionPlane.ts` that re-projects every segment through the parent's `viewMatrix` and emits one world-space `Plane` per segment with a consistent `arrowDirection`.
4. New kernel helper `cutByStepSegments(source, planes, arrowDirection)` in `packages/kernel/src/section/cutBySectionPlane.ts` that runs N sequential `BRepAlgoAPI_Cut_3` calls — one per derived plane — re-using F1's `buildHalfSpace()` unchanged.
5. All faces classified as cut-faces by any segment carry `planeSource: 'section'`. The `'split'` value introduced in F1.1 is NOT extended.
6. `AddSectionViewCommand` payload accepts `mode: 'full' | 'half' | 'stepped'` + `stepSegments?: StepSegment[]`. `apply()` enforces the α-invariant at the command boundary and dispatches to the stepped kernel path when `mode === 'stepped'`.
7. `projectSectionView` filter at `packages/shared/src/drawing/projectSectionView.ts:113` is extended with the α-invariant guard for stepped views.
8. New `ToolMode` value `'pickSteppedSection'` and new `SteppedSectionToolState` sub-state machine in `packages/app/src/drawing/toolMode.ts`.
9. New ribbon button **Stepped Section**, third entry adjacent to **Section** / **Half Section** in `packages/app/src/shell/tabs/DrawingTab.tsx:93–110`.
10. Live SVG polyline overlay during authoring — NO live kernel preview (see §6).
11. Both renderer paths touched same batch: `SectionLineOverlay.tsx` (live React canvas) AND `renderDrawingSvg.ts` (export SVG/PDF/PNG). Applies the F5 "two renderer paths" lesson.
12. E2E spec `tests/e2e/drawing/T-6-13-stepped-section-view.spec.ts`.
13. Perf probe T63d in `tests/perf/section-cut.perf.spec.ts` with p95 < 600 ms at N=4 segments on the 20-component fixture.

### 2.2 Explicitly deferred to F1.2.x (see §12 for full list)

- Combined `stepped + half` (rejected at command boundary).
- Post-create edit (drag jog vertex).
- Oblique (non-90°) jog directions.
- Per-segment hatch styling.
- Live kernel preview during authoring.
- DXF export of stepped section line.

### 2.3 Manifest impact

Manifest stays at **v18**. `stepSegments?` is additive and optional with no backfill needed. No `migrateManifest` entry. Mirrors F5's precedent (`backfillDrawingF5` was data-only, no version bump).

## 3. Worked example

### 3.1 User narrative

Open a part: a cabinet carcass with a **back rebate** — a thin shoulder running across the back where the rear panel sits in a groove. The user wants a section view that:

- Cuts across the cabinet width on the left half (to show the side panel + drawer-rail joinery),
- Then **jogs forward by 30 mm** to clear the back rebate,
- Then continues cutting across to the right edge.

A single planar full-section can't do this — the plane would either miss the rebate entirely or cut through it at the wrong depth. The classical ANSI solution is a **stepped section** (ASME Y14.3 §4.3).

**Workflow.**

1. The user opens the drawing, clicks **Drawing → Place Views → Stepped Section**. The cursor changes to a cross-hair.
2. **Stage 1 — pickParent.** The status bar reads "Click a base or projected view to define stepped-section parent." The user clicks the existing **Front** base view.
3. **Stage 2 — placing.** The status bar reads "Click vertices for stepped section line. Right-click or Enter to finish. Esc to cancel."
   - **Click 1** at the cabinet's left edge, mid-height → first vertex `V0 = (0, 30)`.
   - **Click 2** at `V1 = (60, 30)`. A heavy horizontal line snaps to `V0→V1` (axis-locked X). The cursor's rubber band is now locked to the **vertical** axis (next segment must move only in Y).
   - **Click 3** at `V2 = (60, 60)`. The line jogs upward by 30 mm. The rubber band re-locks to the **horizontal** axis.
   - **Click 4** at `V3 = (120, 60)`. The line extends to the right edge.
4. The user presses **Enter**. The tool dispatches `AddSectionViewCommand` with `mode: 'stepped'` and `stepSegments: [{V0,V1},{V1,V2},{V2,V3}]`.
5. The kernel runs three sequential `BRepAlgoAPI_Cut_3` calls — one per segment-derived half-space — and tags all new cut faces with `planeSource: 'section'`.
6. The projector emits the hatched stepped cut, the section line renders on the parent view as a heavy polyline with arrowheads at the two endpoints and labels **A** / **A** at V0 and V3, and the new section view appears below the parent labelled **SECTION A-A**.

## 4. Data model

### 4.1 New type `StepSegment`

```ts
// packages/shared/src/drawing/types.ts (new export)

export type StepSegment = {
  readonly startSheet: Vec2;   // parent-view-local mm (pre-scale)
  readonly endSheet:   Vec2;   // parent-view-local mm (pre-scale)
};
```

The name `startSheet` / `endSheet` reflects that these are the same coordinate frame as `sectionLine.p0` / `sectionLine.p1` on a full/half section (parent-view-local mm, pre-scale). They are NOT in absolute sheet space; the **`Sheet`** suffix is a vestigial naming carry-over from the brainstorm and should be read as "parent-view-local-mm-space". A future rename to `start` / `end` is acceptable but not in scope.

### 4.2 Extended `SectionView`

```ts
// packages/shared/src/drawing/types.ts (modified, lines 125–158)

export type SectionView = {
  readonly id: string;
  readonly kind: 'section';
  readonly parentViewId: string;
  readonly sectionLine: { readonly p0: Vec2; readonly p1: Vec2 };
  readonly arrowDirection: -1 | 1;
  readonly label: string;
  readonly positionMm: Vec2;
  readonly scale: ViewScale;
  readonly showHidden: false;

  // --- F1.1 ---
  readonly mode: 'full' | 'half' | 'stepped';   // 'stepped' is NEW (F1.2)
  readonly cutSide?: -1 | 1;
  readonly splitPlane?: {
    readonly origin: { readonly x: number; readonly y: number; readonly z: number };
    readonly normal: { readonly x: number; readonly y: number; readonly z: number };
  };

  // --- F1.2 ---
  readonly stepSegments?: readonly StepSegment[];

  // α-invariant (updated for F1.2; see §4.3 for the formal statement):
  //   mode === 'stepped' ⟺ stepSegments !== undefined
  //                      && stepSegments.length >= 2
  //                      && every segment is axis-aligned in parent-2D
  //                      && consecutive segments share an endpoint
  //                      && jog directions alternate (no zero-length jog)
  //                      && cutSide === undefined && splitPlane === undefined.

  readonly plane?: { /* unchanged — present for full and half; absent for stepped */ };
  readonly hatchSegments: readonly HatchSegment[];
  readonly fingerprint: string;
  readonly projection?: { /* unchanged */ };
  readonly inputFingerprint?: string;
  readonly breaks?: readonly BreakRegion[];
  readonly rawProjection?: ProjectedGeometry;
};
```

The `SectionView` shape stays **flat**. F1.1.1 (discriminated union by `mode`) remains deferred. `stepSegments?` is optional at the TypeScript level; the α-invariant is a runtime contract.

### 4.3 α-invariant

> **α-invariant (F1.2):**
>
> `view.mode === 'stepped'` if and only if **all** of the following hold:
> 1. `view.stepSegments !== undefined`.
> 2. `view.stepSegments.length >= 2` (a single segment is rejected — use full Section).
> 3. `view.stepSegments.length <= 8` (max 7 jogs; see §4.5).
> 4. Every segment is axis-aligned in parent-2D: `dx === 0 OR dy === 0` (but not both).
> 5. Consecutive segments share an endpoint: `segments[i].endSheet === segments[i+1].startSheet` for every `i`.
> 6. Jog directions alternate: a horizontal segment is followed by a vertical segment and vice versa. Two consecutive segments along the same axis are rejected (equivalent to a longer segment with a zero-length jog — invalid).
> 7. `view.cutSide === undefined && view.splitPlane === undefined` (stepped + half combo is rejected; deferred to F1.2.2).

Enforced at **three layers** (each raises `'stepped-section-invariant-violated'` on breach):

| Layer | File | Where in code |
|---|---|---|
| Helper layer | `packages/shared/src/drawing/sectionPlane.ts` (new `deriveStepPlanes`) | First operation; throws before any plane derivation. |
| Command layer | `packages/app/src/commands/AddSectionViewCommand.ts` (modified at line ~75–90) | After payload normalisation, before kernel dispatch. |
| Projector filter | `packages/shared/src/drawing/projectSectionView.ts` (modified at line ~113–114) | When a view with `mode === 'stepped'` is processed; throws if the stored segments fail the invariant after a manifest read. |

The triple-layer enforcement is intentional: the helper catches programmatic misuse, the command catches malformed UI payloads, the projector catches corrupt-manifest reads.

### 4.4 Example JSON payload — 2-segment stepped view

```json
{
  "id": "sv-7f3c-stepped-A",
  "kind": "section",
  "parentViewId": "bv-front",
  "sectionLine": { "p0": { "x": 0,   "y": 30 }, "p1": { "x": 120, "y": 60 } },
  "arrowDirection": 1,
  "label": "A",
  "positionMm": { "x": 80, "y": 180 },
  "scale": { "numerator": 1, "denominator": 1 },
  "showHidden": false,
  "mode": "stepped",
  "stepSegments": [
    { "startSheet": { "x": 0,  "y": 30 }, "endSheet": { "x": 60, "y": 30 } },
    { "startSheet": { "x": 60, "y": 30 }, "endSheet": { "x": 60, "y": 60 } },
    { "startSheet": { "x": 60, "y": 60 }, "endSheet": { "x": 120,"y": 60 } }
  ],
  "hatchSegments": [],
  "fingerprint": ""
}
```

Notes:
- `sectionLine` on a stepped view is the line segment from the **first segment's start** to the **last segment's end** (V0 → V3). This is a convenience for `SectionLineOverlay`'s existing arrowhead-and-label logic and for the fingerprint hash. It is **not** authoritative geometry — `stepSegments` is.
- `plane` is absent (stepped views have N planes, not one). The legacy `plane?` field stays optional.
- `cutSide` and `splitPlane` are absent (α-invariant clause 7).

### 4.5 Segment count rationale

| Bound | Value | Reason |
|---|---|---|
| min | 2 segments (1 jog) | A single segment is identical to a full section — user should pick the Section tool, not the Stepped Section tool. Reject for UX clarity. |
| max | 8 segments (7 jogs) | Each segment adds one sequential `BRepAlgoAPI_Cut` (~10–60 ms per call). 8 segments × ~60 ms = ~480 ms, under the 600 ms budget at p95. Beyond 8, the user is approximating a curve — defer to F1.2.7 (offset / aligned). |

### 4.6 No manifest bump

`stepSegments?` is purely additive. v18 manifests written before F1.2 read back identical. v18 manifests written after F1.2 with `mode: 'full' | 'half'` are byte-identical to pre-F1.2 manifests. No `migrateManifest-v18-to-v19` is needed; no `backfillDrawingF1_2` is needed (matches F5).

## 5. Kernel cut strategy

### 5.1 `cutByStepSegments` helper

```ts
// packages/kernel/src/section/cutBySectionPlane.ts (new export)

export function cutByStepSegments(
  oc: OcctInstance,
  source: unknown /* TopoDS_Compound */,
  planes: readonly Plane[],          // N planes, one per segment, ordered V0→V1, V1→V2, ...
  arrowDirection: -1 | 1,            // single direction shared by all segments
): Result;
```

The function runs **N sequential cuts**, one per plane, reusing `buildHalfSpace` unchanged. Each cut removes the half-space on the **away side** (relative to `arrowDirection`) of the segment's plane. The running compound is fed forward.

### 5.2 Pseudocode

```text
function cutByStepSegments(oc, source, planes, arrowDirection):
    if planes.length < 2: throw 'stepped-section-invariant-violated' (count < 2)
    if planes.length > 8: throw 'stepped-section-invariant-violated' (count > 8)

    running = source
    mergedTags = empty FaceTagMap
    anyCut = false

    for i in 0 .. planes.length - 1:
        plane = planes[i]
        halfSpace = buildHalfSpace(oc, plane, arrowDirection)
        result = BRepAlgoAPI_Cut_3(running, halfSpace.handle)
        if !result.IsDone() or no solid in result:
            // Whole stepped cut is empty: signal degraded state
            return { ok: false, reason: 'empty' }

        next = result.Shape()

        // Volume tangent check on per-segment basis
        if abs(volume(next) - volume(running)) < 1e-6 * volume(running):
            // This segment's plane was tangent; preserve running compound, skip merge
            // (Per-segment tangent is non-fatal — a stepped cut with a tangent segment
            //  still produces valid geometry from the other segments.)
            release(next)
            release(halfSpace)
            continue

        // Walk faces of `next`; tag any face within 1e-4 mm of `plane` as
        // cut-face with planeSource: 'section'. All segments share planeSource.
        for face in faces(next):
            key = hashFace(face)
            if classifyFace(face, plane) === 'cut-face':
                mergedTags.set(key, {
                    tag: 'cut-face',
                    partId: '', materialId: '',
                    planeSource: 'section',
                    polygon3D: extractFaceBoundary3D(face),
                })
                continue
            // Preserve prior cut-face tags from earlier segments (don't overwrite as 'original'):
            if mergedTags.has(key):
                continue
            mergedTags.set(key, { tag: 'original-face', partId: '', materialId: '' })

        release(running) unless i === 0   // never delete the caller's source
        running = next
        release(halfSpace)
        anyCut = true

    if !anyCut:
        return { ok: false, reason: 'empty' }   // every segment was tangent

    return { ok: true, compound: running, faceTags: mergedTags }
```

### 5.3 Face-tag contract

| Source plane | Tag | `planeSource` |
|---|---|---|
| Any segment in `stepSegments` | `cut-face` | `'section'` (uniform across all segments — B2) |
| Original part face (no cut) | `original-face` | absent |

Critically, **F1.1's `'split'` value is never produced by `cutByStepSegments`**. The α-invariant rejects stepped+half combo, so a stepped view never has a split plane to tag. F1.1.1 (combined stepped+half) would extend this contract; out of scope for F1.2.

The hatch filter at `projectSectionView.ts:113` already excludes only `planeSource === 'split'`. Because stepped views emit `planeSource: 'section'` uniformly, all their cut faces hatch correctly without filter changes.

### 5.4 Tangent / empty handling

- **Whole-cut empty.** Any segment produces a result with no solid → the entire stepped cut is unrecoverable. Return `{ ok: false, reason: 'empty' }`. `AddSectionViewCommand` surfaces the error toast `'stepped-section-empty-cut'` and the tool stays open with vertices preserved (C3).
- **Per-segment tangent.** A segment's plane is coincident with a face on the running compound (the volume doesn't change). This is non-fatal: skip the segment, continue. The console warns `cutByStepSegments: tangent segment ${i}, skipping`. The remaining segments may still produce a useful cut.
- **All segments tangent.** Caught by the `if !anyCut: return empty` guard at the end. Treated identically to whole-cut empty.

### 5.5 `cutAssemblyByStepSegments` (assembly path)

```ts
// packages/kernel/src/section/cutBySectionPlane.ts (new export)

  oc: OcctInstance,
```

### 5.6 Perf budget (B3)

| Scenario | p95 budget | Rationale |
|---|---|---|
| `cutByStepSegments` + `projectSectionView`, **N=4 segments**, 20-component fixture | **600 ms** | 1.5× F1's 400 ms full-section budget. Four sequential `BRepAlgoAPI_Cut_3` calls — each on a progressively-reduced compound — typically run in ~30–80 ms each on the 20-component fixture. With 4 × ~75 ms cut budget + ~100 ms projection + ~100 ms slack: 500 ms target, 600 ms ceiling. |
| Same, cache hit | **30 ms** | OPFS read + projection only (same as F1/F1.1). |

## 6. Authoring UX

### 6.1 `SteppedSectionToolState` shape

```ts
// packages/app/src/drawing/toolMode.ts (modified at lines 70–89, adjacent to SectionToolState)

export type SteppedSectionToolState =
  | { stage: 'idle' }
  | { stage: 'pickParent' }
  | {
      stage: 'placing';
      parentViewId: string;
      vertices: readonly Vec2[];                 // grows on each click; minimum length 1 (V0)
      lockedAxis?: 'x' | 'y';                    // present once vertices.length >= 1

```

The `mode` value `'pickSteppedSection'` is added to the `ToolMode` union in `packages/app/src/drawing/toolMode.ts:4`. `useToolModeStore` gains a `steppedSectionState: SteppedSectionToolState` field and these actions:

```ts
enterSteppedSectionMode(): void;                   // mode → 'pickSteppedSection', stage → 'pickParent'
steppedPickParent(viewId: string): void;           // stage → 'placing', vertices = []

steppedCommit(onDispatch: (vertices: Vec2[]) => void): void;   // Enter: dispatch + reset
steppedCancel(): void;                             // Esc: clear vertices OR exit mode (two-step)
```

### 6.2 State transitions

| From stage | Action | To stage | Side effect |
|---|---|---|---|
| `idle` (mode set) | enter mode | `pickParent` | Cursor → cross-hair. |
| `pickParent` | click base / projected view | `placing` w/ `vertices=[]`, `lockedAxis=undefined` | First click sets V0 in the same handler tick (see below). |
| `placing` w/ 0 verts | click point | `placing` w/ `vertices=[V0]`, `lockedAxis='x'` (default) | First vertex commits; lock to X axis for next rubber band. |
| `placing` w/ k verts, `lockedAxis='x'` | click point | `placing` w/ `vertices=[V0..Vk_snapped]`, `lockedAxis='y'` | Snap click's `y` to previous vertex's `y`. Flip axis lock. |
| `placing` w/ k verts, `lockedAxis='y'` | click point | `placing` w/ `vertices=[V0..Vk_snapped]`, `lockedAxis='x'` | Snap click's `x` to previous vertex's `x`. Flip axis lock. |
| `placing` w/ k≥2 verts | press Enter | `idle` | Build `stepSegments` from consecutive pairs; dispatch `AddSectionViewCommand`. |
| `placing` w/ <2 verts | press Enter | (no-op) | Status bar warns "Place at least 2 vertices (1 jog) to commit." |
| `placing` | press Esc | `idle` (keep mode = `pickSteppedSection`) | Clear `vertices`; first Esc = clear; second Esc = exit mode. |
| `placing` | right-click | identical to Enter | Convenience binding (matches polyline-tool convention). |

Note: the first vertex `V0` is committed on the **same click** that selects the parent view in `pickParent` mode. After `pickParent`, the handler immediately transitions to `placing` and appends `V0`. Subsequent clicks append further vertices.

### 6.3 Snap behaviour decision tree

The user moves the cursor. The tool emits a snap hint via the rubber-band SVG preview:

```
1. If Shift held: snap disabled. Rubber band = cursor position as-is, BUT
   still axis-locked (the axis lock is independent of snap).

2. Else, snap candidates in priority order (first hit wins):
   2a. Parent view's projected edge ENDPOINTS within 5 px (in screen pixels).
   2b. Parent view's projected edge MIDPOINTS within 5 px.
   2c. Drawing grid (1 mm grid) within 5 px.
   2d. Prior step vertices V0..V(k-1) within 5 px.

3. Apply the axis lock to whatever point came out of step 2:
   - lockedAxis === 'x'  → snap_y = prev.y (rubber band moves only in X)
   - lockedAxis === 'y'  → snap_x = prev.x (rubber band moves only in Y)

4. If the axis-projected point is more than 5 px from the original snap candidate,
   "lose" the snap and just use the axis-locked cursor projection.
```

Decision (C2): when a snap target doesn't lie on the locked axis, **project it onto the locked axis** rather than reject it. This keeps the user's snap intent (e.g. "align with this edge endpoint") while preserving orthogonality.

### 6.4 Axis-lock rules

The lock alternates **strictly**: after `V0` it's X; after `V1` it's Y; after `V2` it's X; and so on. Manual override (e.g. holding Alt to break the lock) is **not** implemented in v1 — locking is mandatory for ANSI compliance (F1.2 ships orthogonal-only per A3). F1.2.1 may relax this.

The initial `lockedAxis = 'x'` after V0 is a convention. If the user's first segment is intended to be vertical, they can place V0 + V1 along Y by:
1. Clicking V0,
2. Moving the cursor → seeing the X-lock rubber band,
3. Holding Shift to disable snap (the rubber band stays X-locked but ignores snap targets),
4. … no — Shift doesn't help. **The user must move along X first**, then jog. If the first intended segment is vertical, they place a zero-length-X segment (V0=V1.x). This is rejected by the α-invariant. To fix this UX paper-cut in v1, we add a single keyboard binding **Tab** that **toggles `lockedAxis` while in `placing` stage with vertices.length === 1** (i.e., only before the second click). After the second click, axis-lock is determined by the segments already placed and Tab is ignored.

### 6.6 Error toasts

| Toast id | Trigger | Recovery |
|---|---|---|
| `stepped-section-invariant-violated` | Helper / command / projector found the α-invariant breached. | Tool returns to `idle`; toast displays "Stepped section invariant breached: <reason>." Dev-mode also logs which clause failed. |
| `stepped-section-empty-cut` | Kernel `cutByStepSegments` returned `{ok:false, reason:'empty'}` after commit. | Tool **stays in `placing`** with vertices preserved (C3). User can adjust last vertex via undo (Esc once) or extend further. |
| `stepped-section-tangent-warn` | Console-only warning when one or more segments were tangent and skipped. The cut still succeeded. | None — informational. |

The `'stepped-section-empty-cut'` recovery is intentionally **non-destructive**: when the user clicks Enter and the kernel finds nothing to cut (e.g., the polyline doesn't actually intersect any part), losing the vertices would frustrate. Instead, the tool stays in `placing` with the existing `vertices` array, lets the user click additional vertices or Esc once to clear and retry.

## 8. Cascade & regen

### 8.1 Parent-view transform cascade

When the parent view regenerates (e.g., the user scales it from 1:1 to 1:2, rotates it, or replaces its underlying part):

1. Each `StepSegment.startSheet` / `endSheet` is **stored in parent-view-local mm (pre-scale)**, so the segments themselves don't need to change.
2. `deriveStepPlanes(stepSegments, parentViewMatrix, arrowDirection)` is invoked with the **new** parent `viewMatrix`. The N world-space planes are re-derived.
3. `cutByStepSegments(source, newPlanes, arrowDirection)` re-runs.
4. `projectSectionView(newCompound, ...)` regenerates the cut + hatch + edges.

This cascade reuses the same trigger that F1's full section already uses (the `RegenerateViewCommand`). No new command is added.

### 8.2 Degraded state

If the re-projected segments yield `{ok:false, reason:'empty'}` after a parent regen (e.g., the user rotated the parent 90° and the polyline no longer intersects the part), the view enters a **degraded state**:

- `view.projection` is preserved from the prior regen (stale data, marked).
- `view.inputFingerprint` is set to `'degraded:stepped-section-empty-cut'`.
- The stale-banner overlay renders ⚠ **"Stepped section: cut is empty after parent change. Edit segments or delete."** atop the section view in the canvas.
- The diagnostic `'stepped-section-degraded-empty-cut'` is emitted to the console + telemetry once per transition.

This matches F1's empty-cut handling: F1 also leaves stale data + ⚠ banner rather than auto-deleting the view.

### 8.3 `RegenerateViewCommand` integration

`RegenerateViewCommand` (the existing command that re-runs the cut+project cascade for a single view) does not need to know about `mode`. It re-dispatches the cut path by inspecting `view.mode` and routing to the matching kernel call:

```ts
// packages/app/src/commands/RegenerateViewCommand.ts (modified)
switch (view.mode) {
  case 'full':    return cutBySectionPlane(...);
  case 'half':    return cutBySectionPlane(..., splitPlane, cutSide);
  case 'stepped': return cutByStepSegments(..., planes, arrowDirection);
}
```

A regression in the F1.1 plan was caught here: if `RegenerateViewCommand` had a `if (view.mode === 'half')` predicate that fell through to a default full-section branch for any unknown value, a stepped view would silently fall back to a full cut. F1.2 makes the branch **exhaustive** (TypeScript `assertNever` on the default case).

### 9.2 OPFS cache key

The cache key for a stepped view extends the F1/F1.1 hash:

where `planeFp_i = fingerprintPlane(planes[i])`. The trailing `::stepped` discriminator prevents collisions with hypothetical future cache keys that share the same plane sequence under a different mode.

## 13. Risks & open questions

### Risk 1 — Boundary artifacts at jog points

**Description (B1 critique).** At each jog vertex `V_i`, two perpendicular half-space planes meet. Sequential `BRepAlgoAPI_Cut_3` calls remove half-space `A` first, then half-space `B`. At the exact jog edge — the intersection line of `A` and `B` planes — OCCT may produce a very small face fragment or a duplicate edge. This is a known fragility of sequential half-space cuts vs. a single multi-tool boolean.

**Mitigation.** Three guards:
1. The face classifier (`classifyFace`) uses a 1e-4 mm tolerance — fragments smaller than this are merged into adjacent faces by OCCT's internal cleanup.
2. The per-segment volume-tangent check (§5.4) catches the degenerate case where the second cut's plane is coincident with a face produced by the first cut.
3. Post-cut, `BRepAlgoAPI_Cut_3` already runs a `Build()` step that merges co-planar faces. The output is canonical enough for the projector.

If artifacts persist in real geometry, F1.2.x could switch to `BOPAlgo_Builder` with all N half-spaces as a single tool set. Out of scope for v1.

### Risk 2 — Perf budget guess vs measure

**Description (B3 critique).** The 600 ms budget at N=4 is a 1.5× extrapolation from F1's 400 ms full-section budget. It assumes each cut is on a progressively-reduced compound (so cut 2 is faster than cut 1, etc.). On real geometry with many fillets / holes, the per-cut time may not decrease — the compound retains complexity even after volume reduction.

**Mitigation.** Measure first; tighten later. The T63d perf test is set to the loose 600 ms bound. After F1.2 ships, the 30-day p95 telemetry from real user sessions will be inspected; the budget can be tightened in a follow-up PR (matches F1's 400 ms — actually measured ~29 ms — pattern).

### Risk 3 — Parent-rotation cascade pushing segments off part

**Description (D1 critique).** `stepSegments` are stored in parent-view-local mm. If the user rotates the parent view 90° (changing its `viewMatrix`), the segments stay at the same 2D coords — but the part now occupies a different 2D region. Segments that previously bisected the part may now miss it entirely.

**Mitigation.** The degraded-state handling per §8.2 catches this: the view enters degraded mode with a ⚠ banner, prompting the user to edit the segments. The user has clear visual feedback (the cut-empty banner) and a recovery path (delete the stepped view + recreate after the rotation).

A more graceful alternative — auto-transforming `stepSegments` through the parent's rotation matrix to follow the part — is **rejected** because (a) it's ambiguous (which axis of rotation do we follow?), (b) it would invalidate the α-invariant clause 4 (axis-aligned) under arbitrary rotation, and (c) users typically don't rotate parents after creating dependent section views.

### Open question 1 — Should the first axis-lock default to X or "free until first click"?

Currently: locked to X after V0 with Tab as escape hatch. Alternative: free until V0+V1 (the first segment determines the axis). The alternative is cleaner but requires a rubber-band that follows the cursor freely until V1, then snaps to axis-locked thereafter. Either works; the spec picks the simpler "always locked + Tab toggle" for v1. Revisitable in F1.2.x.

### Open question 2 — Should `sectionLine` on a stepped view be filled with V0→V_last, or left undefined?

The spec mandates V0 → V_last for ergonomic reuse by `SectionLineOverlay`'s existing label/arrowhead logic. The alternative — leaving `sectionLine` undefined and adding a `?` to it on the type — propagates `undefined` checks throughout the codebase. The chosen approach is a "vestigial but harmless" field; the cost is one extra field of redundancy, the saving is dozens of `?.` checks. Acceptable.
