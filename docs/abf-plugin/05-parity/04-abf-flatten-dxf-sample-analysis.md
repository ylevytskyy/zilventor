# ABF flatten DXF — sample-file convention analysis

**Provenance.** Sample file `Стелаж 123` (a "flatten"/flat-drawing export produced by the ABF plugin) was received 2026-07-04 in the user's Downloads folder; a working copy was analyzed forensically in a scratch directory (not committed to this repo). The file is `AC1021` (AutoCAD 2007 DXF format), plain ASCII/UTF-8 text, ~903KB, and encodes a shelving unit ("Стелаж" — Ukrainian for shelf/rack unit) that includes doors. All findings below are drawn from group-code-level parsing of the file with ad-hoc Python scripts (a hand-rolled group-code reader, not a DXF library) — every number and string cited here comes from that parsing, not from visual inspection or guesswork, except where explicitly flagged `UNCERTAIN`.

This document is a sibling to [`01-zilinventor-capability-inventory.md`](01-zilinventor-capability-inventory.md), [`02-gap-analysis.md`](02-gap-analysis.md), and [`03-processing-parity-requirements.md`](03-processing-parity-requirements.md), but unlike those (built from marketing/tutorial/forum research), this one is built from a **real ABF-produced DXF file** — it is the first primary-source, byte-level evidence in this parity series and should be weighted more heavily than the earlier research-derived claims wherever they conflict.

## 1. Document structure

- **`$ACADVER = AC1021`** (AutoCAD 2007 DXF variant, Unicode-DXF era). **`$INSUNITS = 4`** (millimeters). **`$MEASUREMENT = 1`** (metric). **`$DWGCODEPAGE = ANSI_1251`** is present in the HEADER but appears to be **vestigial/unused** — the file's actual text encoding is genuine UTF-8, not cp1251. Confirmed directly: the `ATTRIB` tag `Skp_GroupInstanceName` carries values like `__4. Дверка` (door) which decode cleanly as UTF-8 with no escape sequences or cp1251 remapping needed.
- **`$EXTMIN`/`$EXTMAX` are unfilled AutoCAD sentinel values** (≈ ±1×10²⁰), i.e. the exporter never walked the nested block tree to compute a real bounding box. A parser must **recompute the geometric extent itself** by resolving all nested `INSERT`s. Doing so for this file gives an actual bbox of roughly **x ≈ −7702..0 mm, y ≈ −33..1431 mm**.
- **Geometry lives almost entirely in the `BLOCKS` section, not `ENTITIES`.** Of ~57,900 total group-code pairs in the file, ~45,600 are inside `BLOCKS`; the `ENTITIES` (modelspace) section holds only ~101 pairs — just **3 top-level `INSERT` entities**, all placed at `(0,0,0)`.
- **The BLOCKS section is a deeply-nested SketchUp component/group tree**, carried through verbatim rather than flattened: **184 `BLOCK` definitions** total, nested up to ~5 levels deep. The naming pattern is `<MATERIAL>_THICKNESS_<mm>` (e.g. `AUTO_THICKNESS_18`, `SREE_PEARLS_2_THICKNESS_18`) at the top, each containing one `Group<N>#<M>` block per physical panel, each of which contains further nested `Group<N>#<M>` sub-blocks for the panel's edge-quads, hardware symbols, and label geometry. This is confirmed to be a direct passthrough of SketchUp's internal component/group hierarchy: `ATTRIB` tags are literally named `Skp_ComponentInstanceName` and `Skp_GroupInstanceName` (the `Skp_` prefix = SketchUp).
- **Layout is "one instance per real panel," not sheet-nesting.** There are **10 unique panels** total in this sample (6 under `AUTO_THICKNESS_18`, 4 under `SREE_PEARLS_2_THICKNESS_18`). Each material group additionally carries one `DIMENSION` + one `MTEXT` (Tahoma font) giving a group-level overview width label — this is NOT per-panel dimensioning, just a summary annotation per material group. This is a "flatten" export of the individual panels of one cabinet, not a nested sheet-layout/cutting-diagram export (that would be a separate ABF export mode, not sampled here).

**Interpretation for an ABF-compatible exporter:** the BLOCKS-centric, SketchUp-passthrough structure means ABF's "flatten" DXF is essentially a serialization of SketchUp's internal scene graph, not a purpose-built flat 2D drawing format. A from-scratch ABF-compatible exporter does **not** need to replicate the block nesting depth — it only needs to replicate the **layer-naming grammar** (§3) and **feature geometry conventions** (§4), which are the parts of the file that carry manufacturing semantics.

## 3. Layer-name grammar — convention rules

The following rules are stated as an engineer could implement against them. Every rule is evidence-backed from §2 unless marked `UNCERTAIN`.

1. **`DEPTH<mm:decimal>-ARTICLE<sku:integer>`** — `<mm>` is the hardware's drill **depth** in millimeters (matches the layer's semantic role, not necessarily the drawn geometry); `<sku>` is a catalog article/SKU id for a specific hardware part. **Diameter is NOT encoded in the name** — read it from the `CIRCLE`'s group-40 radius × 2. **Face-vs-edge orientation is also NOT reliably implied by this family name** — e.g. `DEPTH12-ARTICLE38877` (8mm) is 100% edge-oriented despite using the DEPTH-ARTICLE naming, while `DEPTH13-ARTICLE96053` (35mm hinge cup) is 100% face-oriented. **Orientation must be read per-instance from the CIRCLE's extrusion vector** (see Rule 5), never inferred from the layer-name family alone.
2. **`ABF-DSIDE-<dia:decimal>`** — `DSIDE` reads as "drilled side" (i.e. side/edge boring). Here the diameter **IS** encoded in the name and it matches the geometry exactly in both sampled instances (`ABF-DSIDE-8` → 8.0mm circles; `ABF-DSIDE-4.5` → 4.5mm circles). Confirmed 100%/65% edge-oriented respectively. Each bore on this layer family is duplicated as a `CIRCLE` plus a companion `POLYLINE` — the purpose of the polyline duplicate is **UNCERTAIN** (possibly a witness/centerline mark or a tool-path outline; not confirmed).
3. **`D<n:decimal>-DEPTHF-$<sku:integer>`** — `<n>` is the bore diameter and matches the geometry exactly (`D7` → 7.0mm circles, confirmed). `DEPTHF` meaning is **UNCERTAIN** — plausibly "depth-from-face" or a distinct hardware sub-family from plain `ARTICLE`, but this is a guess based on a single instance. The `$`-prefixed number is a second, differently-namespaced SKU/article id — **UNCERTAIN** whether this denotes a genuinely separate hardware catalog source from the plain `ARTICLE<sku>` layers, or just a different ID scheme for the same catalog.
4. **`DEPTH3.0`** — a bare depth value with no article/SKU suffix at all (2.0mm-diameter circles, 50/50 face/edge split). **UNCERTAIN** why this one family lacks an article number — possibly a generic/no-specific-hardware bore (e.g. a pilot hole or shelf-pin-adjacent bore) rather than a named catalog part.
5. **`ABF_cuttingLines`** — the panel outline layer. Each panel edge is represented as a duplicate pair: a `LINE`/legacy-`POLYLINE` on this layer with **non-zero Z** (Z spans 0 → panel thickness, e.g. 18.0mm) tracing the edge as a 3D silhouette of the board's thickness face, not a flat 2D line — plus a flat (Z=0) duplicate on `Untagged00`, which appears to be a rendering artifact rather than load-bearing content. Treat `ABF_cuttingLines` as authoritative for reconstructing the panel's 2D footprint (take the outline at Z=0 or project to the XY plane).
6. **`ABF_Label`** — see §4 (labels are NOT plain text on this layer; the human-readable string is exploded into stroke geometry).
7. **`Untagged00`** — appears to be exporter-internal/derived geometry (flat duplicate panel-edge outlines), not independently meaningful; **UNCERTAIN** whether this layer ever carries anything else in other ABF exports.
8. **`Defpoints`** — standard AutoCAD auto-generated layer for `DIMENSION` definition points, not ABF-specific content; safe to ignore in a from-scratch exporter unless replicating `DIMENSION` entities too.
9. **`0`** — the default/administrative layer. Carries the 3 top-level `INSERT`s, their `ATTRIB`s (SketchUp instance-name metadata, see §4), the 2 group-overview `DIMENSION`/`MTEXT` pairs, and a handful of `SOLID`/`LINE` entities that appear to be UI/annotation chrome rather than manufacturing geometry.

## 4. Feature representation

- **Panel outlines**: NOT a single closed `LWPOLYLINE` per panel. Instead, each panel edge is drawn as a separate `LINE`/legacy-`POLYLINE` segment on `ABF_cuttingLines` (with non-zero Z, per Rule 5 above), duplicated flat on `Untagged00`. A parser needs to reconstruct the closed polygon by joining these per-edge segments at Z=0, not by reading a single ready-made polygon entity.
- **Face bores** (drilled through the panel's thickness face, e.g. hinge cups, shelf-pin holes on `Top`/`Bottom`-style faces): represented as `CIRCLE` entities with extrusion vector `(0, 0, ±1)`. Verified example: the 35mm hinge cups on `DEPTH13-ARTICLE96053` sit at extrusion `(≈0, ≈0, −1)`, and once the OCS mirror correction (§5) is applied, their centers fall an inset of **22.5mm from the panel edge** — the standard concealed-hinge cup-to-edge distance, which is strong corroborating evidence the geometry and the correction are both right.
- **Edge/side bores** (drilled from the panel's thin edge, e.g. shelf-pin System-32 rows or side-panel joinery): represented as `CIRCLE` entities with an in-plane extrusion vector (Z-component ≈ 0). The `ABF-DSIDE-<dia>` family is the clearest, purest example of this (100% edge-oriented in both sampled instances). These circle centers sit at or very near the panel's edge/boundary coordinates rather than deep inside the face footprint, consistent with edge-drilling geometry rather than face-drilling.
- **Grooves/dados**: **none found in this sample.** All 60 `Untagged00` `POLYLINE`s are accounted for by the panel-edge-quad duplication described above (~6 per panel × 10 panels) — none of them describe a rectangular groove/dado shape. **UNCERTAIN** whether ABF has a groove/dado DXF convention at all, or this particular cabinet design simply doesn't use grooved joinery; this sample cannot answer that question either way.
- **Labels**: the `ABF_Label` layer's content is **exploded into ~1280 raw `LINE` stroke segments** (vector/stick-font glyphs) — it is NOT a `TEXT` or `MTEXT` entity, so there is no readable DXF string on this layer to parse directly. The actual machine-readable per-part identity instead lives on the `ATTRIB` tag `Skp_GroupInstanceName` (and `Skp_ComponentInstanceName`) attached to each panel's `INSERT`, which decodes cleanly as UTF-8 Cyrillic/Ukrainian text. Confirmed decoded examples: `__4. Дверка` (door), `__9. Дно` (bottom), `__11. Бік Пр` (side, right), `__13. ЗАД` (back). The apparent format is `__<index>. <short part name>` — an ordinal index followed by a period-space and a Ukrainian/Russian abbreviation of the part's role in the cabinet (door/bottom/side/back, etc.); no width×height dimension or material code was observed appended to these specific sample strings, though the group-level `MTEXT` (§1) does separately carry an overview width figure.

## 5. The OCS/extrusion finding (highest implementation priority)

Hardware-symbol `CIRCLE` entities (hinge cups and others) are authored with extrusion vector **`(210,220,230) ≈ (0, 0, −1)`**. Per AutoCAD's Arbitrary Axis Algorithm, an extrusion of exactly `(0,0,−1)` is the one case where the OCS (Object Coordinate System) X-axis is **mirrored** relative to WCS: `Xworld = −Xocs` (Y and Z pass through unchanged). A naive parser that only applies the containing `INSERT`'s translation and rotation — and ignores this per-entity OCS correction — will place bore centers **outside the panel entirely**.

This was verified concretely: resolving one hinge-cup circle's coordinates through only the INSERT transform gave `x ≈ −25.5` against a panel whose footprint spans roughly `x ∈ [−3, 316]` — clearly outside. Applying the OCS mirror correction *before* the INSERT transform gives `x ≈ +19.5`, which is a sensible 22.5mm inset from the panel edge — the industry-standard hinge cup-to-edge distance, and consistent with the confirmed diameter and layer (§4).

**Rule 5 (mandatory for a correct exporter/importer):** for any `CIRCLE`/`LINE`/etc. whose extrusion vector is `(0,0,−1)` (within floating-point tolerance), apply `Xworld = −Xocs, Yworld = Yocs, Zworld = Zocs` **first**, then apply the entity's containing `INSERT` translation/rotation/scale chain. Skipping this step is the single most likely source of a silently-wrong bore-position bug in an ABF-compatible import or export path.

## 6. Uncertainties and limitations

- **Single-sample evidence.** This entire analysis rests on one file describing one 10-panel cabinet. Layer families that appear only once (`D7-DEPTHF-$44817`, `DEPTH3.0`) cannot be generalized with confidence — their token semantics (`DEPTHF`, the bare no-article `DEPTH<mm>` form, the `$`-prefixed SKU namespace) are inferred, not corroborated across multiple examples.
- **No groove/dado convention observed.** Absence of evidence here is not evidence of absence — this cabinet's design may simply not use grooved joinery; a sample containing a dado/groove is needed before any groove-layer convention can be documented.
- **Possible AutoCAD re-save.** The file's `$LASTSAVEDBY`-equivalent metadata (per the coordinator's note) suggests the file may have been re-opened and re-saved in AutoCAD (a generic `User`) rather than being the pristine, unmodified output of the ABF plugin itself. If so, some structural details (e.g. exact `$ACADVER`, whether `$DWGCODEPAGE` was already stale before the re-save, entity ordering) could reflect AutoCAD's re-serialization rather than ABF's native export behavior. This does not appear to affect the layer-naming or geometry findings, which are ABF-authored content, but it is a caveat on any claim about the *exact* byte-level export format ABF itself produces.
- **DSIDE companion-polyline purpose unconfirmed.** Every bore on the `ABF-DSIDE-<dia>` layers has both a `CIRCLE` and a `POLYLINE` at the same location; this document guesses "witness mark / centerline / toolpath outline" but did not confirm which.
- **OCS correction validated once.** The Rule-5 mirror correction is confirmed against exactly one example (the 35mm hinge cup, corroborated by the known 22.5mm industry-standard inset). It has not been cross-checked against a second, independently-verifiable hardware type in this sample.
- **No ABF-custom XDATA found.** Only stock AutoCAD application XDATA is present (`ACAD_MATERIAL_MAPPER`, `DSTYLE`, `ACAD_MLEADERVER`) — part/hardware identity in this file is carried entirely through layer names and `ATTRIB` tags, not through extended entity data. This sample gives no evidence either way about whether other ABF export modes (e.g. a dedicated nesting/CAM export) use XDATA.

**Confidence: 75** — the document-structure and layer-grammar findings (§1–§4) are strongly evidence-backed by direct group-code parsing and cross-checked geometry (diameter-matches-name, hinge-inset distance). The OCS/extrusion finding (§5) is validated by one clean, independently-plausible example and is high-confidence as a *mechanism* (it follows directly from the documented AutoCAD Arbitrary Axis Algorithm) even though only single-instance-verified in this file. The main drag on confidence is single-sample coverage: several layer-name tokens (`DEPTHF`, `$`-prefixed SKU, bare `DEPTH3.0`) and the DSIDE companion-polyline purpose are inferred from one occurrence each and would need a second, more varied sample file to firm up.

## 7. Gap analysis vs. ZilInventor's own DXF conventions

Synthesized 2026-07-04 against the shipped export/import code (`packages/app/src/drawing/manufacturingLayers.ts`, `renderPanelManufacturingDxf.ts`, `renderNestSheetDxf.ts`, `packages/shared/src/dxf/`). This section supersedes the "CNC export gap" table in [`02-gap-analysis.md`](02-gap-analysis.md) wherever they conflict — that table was built from secondary sources; this one is built from the sample file.

| Aspect | ABF flatten DXF (this sample) | ZilInventor manufacturing DXF |
|---|---|---|
| DXF version | AC1021, ASCII, UTF-8 text | AC1015, ASCII (writer: `dxfWriter.ts`) |
| Overall structure | SketchUp scene-graph passthrough: 184 nested `BLOCK`s, 3 modelspace `INSERT`s | Flat purpose-built entities in `ENTITIES`; anonymous blocks only for `DIMENSION` |
| Panel outline | Per-edge `LINE`/legacy-`POLYLINE` segments on `ABF_cuttingLines`, 3D silhouette (Z spans thickness); polygon must be reconstructed | One closed `LWPOLYLINE` on `OUTLINE`, panel-local mm, Z=0 |
| Face bores | `CIRCLE`, extrusion `(0,0,±1)`, on `DEPTH<depth>-ARTICLE<sku>`; **diameter in geometry, depth+SKU in layer name** | `CIRCLE` on `BORES-FRONT/BACK-<dia>MM`; **diameter in layer name, depth in XDATA/machining.csv**, no SKU channel |
| Edge bores | `CIRCLE` (in-plane extrusion) + companion `POLYLINE` on `ABF-DSIDE-<dia>` | `CIRCLE` on `BORES-EDGE-<edge>-<dia>MM` (edge ∈ Front/Back/Left/Right) |
| Hardware identity | Catalog SKU in the layer name (`ARTICLE<sku>` / `$<sku>`) | No SKU in DXF; `toolNumber`/`speed` via `ZILVENTOR` XDATA + `machining.csv` sidecar |
| Grooves | Not observed (see §6) | Closed `LWPOLYLINE` on `GROOVES` |
| Labels | Exploded stick-font `LINE` strokes on `ABF_Label` (no text entity); machine-readable identity in `Skp_*` `ATTRIB`s | `TEXT` entities on `INFO`/`BORE-INFO` |
| Metadata | No custom XDATA; layer names + `ATTRIB`s carry everything | `ZILVENTOR` APPID XDATA on machining entities |

**Import-path implications (reading ABF files into ZilInventor).** The parser (`packages/shared/src/dxf/parser.ts`) is version-agnostic and reads AC1021 fine; encoding is a non-issue (the file is genuine UTF-8, and our `file.text()` decode assumes UTF-8). But two concrete defects would bite today:

1. **The §5 OCS bug is live in our importer.** `toSketch.ts` implements the Arbitrary Axis Algorithm (`ocsXY`/`ocsReflected`) for top-level entities, but explicitly defers the exact case this file exercises — `toSketch.ts:293`: *"Block-internal entities ignore their own OCS extrusion under an insert (rare, deferred)."* ABF's bore circles are all block-internal with extrusion `(0,0,−1)`, so importing this sample would silently misplace every face bore (the failure mode predicted in §5).
2. **`ATTRIB` is not parsed** — the `Skp_GroupInstanceName` part names (the only machine-readable panel identity in the file) would be dropped.

**Export-path implications (an "ABF-compatible layer scheme" mode).** Per §1's interpretation, only the layer grammar and feature-geometry conventions carry manufacturing semantics, so an ABF-compatible export does **not** need block nesting, exploded stick-font labels, or the 3D-silhouette outline style. The existing `presetLayerName` override already lets a user hand-route any single feature to an ABF-style layer name; a systematic mode would map: face bores → `DEPTH<depth>-ARTICLE<sku>` (SKU available only for catalog-hardware-originated bores; bare `DEPTH<depth>` otherwise, per Rule 4), edge bores → `ABF-DSIDE-<dia>`, outline → `ABF_cuttingLines`. Open design questions (scope, SKU sourcing, groove handling given §6) are deliberately not resolved in this document.
