# Gap Analysis: ABF vs. ZilInventor by Aspect

This document lines up ABF's demonstrated capabilities against ZilInventor's current codebase, aspect by aspect. It draws on [`05-parity/01-zilinventor-capability-inventory.md`](01-zilinventor-capability-inventory.md) for the ZilInventor side and on the `01-overview/`, `02-model-setup/`, `03-machining/`, `04-production-output/` docs for the ABF side. Where a claim from the source research was only "plausible" or "unverified," that qualifier is repeated here rather than stated as fact.

Scope note: ABF is a SketchUp plugin bolted onto a generic 3D modeler with no native parametric history. ZilInventor is a parametric CAD kernel with its own sketch/feature/assembly model. Some comparisons are therefore not apples-to-apples — flagged as "not-comparable" where that matters.

## Model-setup gap: ABF's rigid Solid-Group input contract vs. ZilInventor's native part/assembly model

ABF is bolted onto SketchUp, a non-parametric modeler with no first-class "part" concept. To compensate, ABF imposes a strict input contract on the user: every panel must resolve to a single-level SketchUp **Group** (not a Component — ABF reportedly "does not work with components at all" per one tutorial), must be a true watertight solid, and should be named with a full material code before any ABF tool is run. ABF ships conversion tools ("Convert Component to Group," "Face to Group") specifically because users routinely violate this contract by importing libraries or building with Components. Grain direction is a separate manual attribute (rotate a label, independent of the visual material/UV), and label placement doubles as an implicit geometry-validity check — if a label fails to attach, the panel geometry is probably broken.

ZilInventor does not need any of this. Panels are native kernel geometry produced by the feature tree (sketch → extrude → etc.), so there is no "is this a Group vs. a Component" ambiguity, no manual grain-direction attribute (grain is presumably tied to material/board orientation in the part definition), and no separate conversion/validation pass before manufacturing tools can run. This is a structural advantage: ZilInventor's model-setup gap versus ABF is effectively "we don't have this problem," not a feature we're missing.

**Requirement framing (if ZilInventor ever needs to interoperate with externally-modeled/imported geometry, e.g. STEP import treated as raw solids):** when accepting non-native panel geometry, validate it is a closed manifold solid and flag ambiguous/self-intersecting geometry before it enters the manufacturing pipeline — this is the one genuinely portable idea from ABF's contract (fail loud on bad geometry), not the Group/Component distinction itself, which is SketchUp-specific and not applicable to ZilInventor's kernel.

## Machining gap: ABF's configurable-preset hardware catalog + toolNumber/speed metadata vs. ZilInventor's fixed connector catalog

Both tools cover a comparable spread of hardware types (confirmat, cam/eccentric, dowel, Minifix, Rafix, Cabineo, Lockdowel, hinges, shelf pins, drawer slides). The real gap is in **metadata depth and configurability**, not coverage breadth:

- **Per-type parameter presets.** ABF's developer states directly (forum, unverified beyond that single quote) that hole parameters and their target DXF layer name are user-configurable per hardware type and savable as presets. ZilInventor's `BUILTIN_CATALOG` is a fixed 16-SKU list; per-document customization exists only via the M4 Slice D JSON import path (`resolveHardwareCatalog`), which is a bulk swap-in of new SKUs, not a live in-app "edit this hole's diameter/depth/layer and save as a preset" UX.
- **Tool/toolpath metadata.** ABF associates each defined cutting tool with a `toolNumber` (physical tool-magazine slot) and a machining speed, and distinguishes "Profile Toolpath" (contour) from "Pocket Toolpath" (recess) — this is metadata aimed at keeping the DXF/CAM hand-off in sync with a specific CNC's physical tool loadout. ZilInventor's manufacturing DXF (M2.1) has layers named by operation and diameter (`BORES-FRONT`, `EDGE-<dia>MM`, `GROOVES`) but carries no tool-number or feed/speed metadata — that translation from "which layer" to "which physical bit at what speed" is left entirely to the CAM operator's own setup, same as ABF's *current* shipped state (its own richer "DXF/XML Tổ Hợp" combined export with this kind of embedded metadata is itself unshipped/roadmapped, not something ABF users have today).

**Requirement:** if ZilInventor wants to close this gap, the actionable target is not "add more hardware SKUs" (already comparable) but (a) an in-app editable hole-parameter-per-hardware-type UI backed by savable presets, and (b) optional tool metadata (tool number, speed) attached to manufacturing-DXF layers, exported as extended entity data or a sidecar CSV. Neither is urgent — ABF itself hasn't shipped the second one either.

**Groove/joinery structural note:** ZilInventor's `GrooveFeature` is a genuine regenerable parametric feature (re-executed via `BRepPrimAPI_MakeBox` boolean cut on every model rebuild). ABF's groove/joinery mechanism ("Mark Intersection") is a geometry-intersection marker applied once to static SketchUp geometry — there is no evidence it re-runs automatically when the model changes. This is a case where ZilInventor's underlying parametric architecture makes its *equivalent* feature more robust, even though the user-facing capability (cut a groove) looks similar on paper. One functional gap: ABF supports full mortise/tenon joinery (auto-generated matching male/female cutouts across two panels); ZilInventor has raised-panel door rebate grooves but no general-purpose tenon/mortise generator — see also `03-machining/02-hardware-boring-and-joinery.md`.

## Nesting gap: ABF's reference-only Quick-Nesting (soon PRO) vs. ZilInventor's already-shipped kerf/oversize guillotine nesting — where ZilInventor is AHEAD

This is the clearest case of ZilInventor being ahead of ABF, not behind it. ABF's own vendor site states its free "Quick - Nesting" tool shows only the result of the **first calculation pass** — explicitly not an optimizing/iterating engine — and is "reference-only" for material ordering. A more advanced "PRO" nesting tier is stated to be "in development," with no shipped date, pricing, or feature list confirmed. ABF's saw-oriented cutting-diagram feature (the closer analogue to a true guillotine cut-map with cut-sequence display) is on the roadmap but explicitly **paused due to low demand** — i.e., not available at all today.

ZilInventor already ships `packGuillotine`: a guillotine-cut packer with kerf allowance, per-job oversize allowance (Milestone 1b.2), multi-material packing (`packAllMaterials`), and staleness detection (`computeNestFingerprint`) that re-flags a nest when the cut-list, kerf, or oversize setting changes. Output covers PNG, PDF, and DXF (M2.2), all zip/multi-sheet capable. This is materially more capable than what ABF's free tier offers today, and arguably comparable to what ABF's *unshipped* PRO tier and *paused* cut-diagram feature are aiming for.

The one place ABF is ahead: interactive manual nesting-result editing (MORO + FIND — drag, rotate, flip individual nested parts after the automatic pass) and remnant/offcut labeling ("MORO - Last cut"). ZilInventor's inventory doesn't document an equivalent interactive nest-editing UI or remnant tracking — flagged as an open question rather than a confirmed gap, since the capability inventory may simply not have surfaced it.

**Verdict: ZilInventor ahead on core nesting algorithm and export maturity; possible minor gap on interactive nest-editing and remnant tracking (unconfirmed).**

## CNC export gap: ABF DXF-only with per-material/combined modes and arc interpolation vs. ZilInventor's R12 DXF — format-detail deltas to close

Correction to the outline's framing: ZilInventor's DXF codec targets **AC1015 (AutoCAD 2000+)**, not R12 (AC1009) for the drawing-system DXF — the M1 milestone's own capability note in the inventory states "strict AC1015." (An earlier standalone drawing-DXF feature, `project_drawing_dxf_export_feature`, did originally hand-roll R12/AC1009 output, but the current bidirectional M1 DXF codec is AC1015. Where this document's outline says "R12 DXF," read it as "ZilInventor's current DXF export," not a literal claim that the shipped format is R12.) ABF's DXF version is not confirmed by any primary source — a third-party blog's claim of "R2010" is explicitly flagged as unverified/uncorroborated in the source research.

Both tools are DXF-only for CNC output — neither ships MPR, XNC, CIX, or any other CAM-native format. ZilInventor's CIX support is explicitly deferred pending a real sample file (per the inventory); ABF's roadmap only gestures at "other machine manufacturers' input standards" generically, unshipped.

**Update (2026-07-04):** a real ABF flatten DXF sample has since been analyzed at byte level — see [`04-abf-flatten-dxf-sample-analysis.md`](04-abf-flatten-dxf-sample-analysis.md), whose §7 gap table supersedes the format-detail deltas below wherever they conflict (it confirms ABF's version is AC1021, documents the actual layer grammar, and EXEC-verifies ZilInventor's importer resolves the file class's block-internal OCS extrusion correctly; `ATTRIB` part-name parsing shipped 2026-07-04, so the file class imports with panel identity intact).

Confirmed deltas:

| Detail | ABF | ZilInventor |
|---|---|---|
| Export granularity | Per-material folders OR single combined file (user choice, whole-nest-result scope) | Per-unique-panel ZIP (M2.1, dedup by size+material+grain+boring+grooves signature) + separate per-sheet nesting DXF (M2.2) | 
| Arc/curve representation | Vendor confirms "circularly interpolated" (true arcs, not polyline-tessellated) — unverified whether this means native ARC/CIRCLE entities | Not explicitly stated in the inventory; ZilInventor's general DXF codec (M1) supports native entities including arcs as part of full 2D drawing import/export, so likely comparable, but not confirmed for the manufacturing-DXF (M2.1) path specifically |
| Layer naming | User-configurable per hardware type/settings | Fixed taxonomy: `OUTLINE`, `BORES-FRONT/BACK`, `EDGE-<dia>MM`, `GROOVES`, `EDGEBAND`, `GRAIN`, `INFO`, `DIMENSIONS`, `BORE-INFO` (M2.1); `SHEET`/`OUTLINE`/`INFO` (M2.2) | 
| Embedded hardware/hole positions | Ambiguous/unshipped — vendor's own roadmap lists "edge-drilling positions + labels in DXF/XML" as **not yet built**; current export may only carry hardware via separate `ABF_`-prefixed marker sub-groups (unconfirmed) | Shipped — bores rendered as circles on diameter-coded layers (`BORE-INFO`, `EDGE-<dia>MM`) | ZilInventor is ahead here, confirmed |
| Character encoding | Not specified | ASCII-only text in machining/nesting DXFs (Cyrillic not supported there, though supported elsewhere in the app's i18n) | Known ZilInventor limitation, not an ABF comparison point |
| Color palette | Not specified | Sparse common ACI palette only, not full 256-color | Known ZilInventor limitation |
| ATTRIB/ATTDEF block attributes | Not specified | Not imported | Known ZilInventor limitation |
| Real-CAD-app open verification | Not specified | Never independently confirmed in a real CAD app (human-gated, unverified per inventory) | Shared open risk on both sides — no primary source confirms either tool's DXF has been opened in AutoCAD/BricsCAD and checked |

**Verdict: parity on "DXF is the only format," ZilInventor ahead on embedded hardware-position data (the one thing ABF explicitly hasn't shipped yet), ABF possibly ahead on per-type layer-name configurability (unconfirmed) and confirmed true-arc interpolation (ZilInventor's manufacturing-DXF arc fidelity is unverified).**

## Labels/reports gap: ABF's preset-driven print templates + QR + Statistics vs. ZilInventor's PDF shop labels — feature deltas

Both tools produce a similar core artifact: a printable per-panel label with part identity, dimensions, material, and a QR code. Confirmed deltas:

- **Templates.** ABF offers multiple label templates (at least 3, with template #3 adding QR) plus a header area with two free-text lines saved as named, filterable, editable presets. ZilInventor's M2.3 label is a fixed 2×5-grid A4 layout with one label per physical panel copy — no template selection or free-text preset system found.
- **Edge-band cross-reference.** ABF moved verbose per-edge band-code text off the main label onto a separate companion "tem Note" label (deliberate declutter). ZilInventor's label instead shows banded-edge thickening + F/B/L/R letters directly on the mini panel diagram — a different (arguably more compact) design choice, not a gap per se.
- **QR payload.** ABF's QR format is `ID.text` (numeric ID + text, parsed by the downstream web tools). ZilInventor's QR payload is a structured pipe-delimited string (`Z|item|copy/qty|LxWxT|materialName`) — richer inline data, but with no corresponding downstream scanning tool (see below).
- **Downstream reconciliation tools — confirmed ABF-only gap.** ABF hosts two web apps at getabf.net that consume the QR-coded label + exported Excel: "Qr Checker" (scan each produced panel, mark status, re-export) and "QR Package Checker" (build a packing list/delivery slip per batch, with configurable company/customer template fields). ZilInventor has no equivalent shop-floor reconciliation or packing-slip tool — the QR code is generated but nothing in the inventory consumes it downstream.
- **BOM/Statistics.** ABF's "Thống Kê" computes per-item unit price → total cost → a formal price quote ("báo giá"), and exports to Excel. ZilInventor's `aggregateBomRecursive` + CSV export covers hardware/connector counts and cut-list gross sizes but the inventory finds "no native PDF cut-list/purchase-order report format" and no unit-price/quote calculation — this is a confirmed feature gap.
- **Custom statistical objects.** ABF's "ABF DC - Thêm Thống Kê" lets users embed custom count/length objects into library components so non-standard parts (e.g. a closet rod) roll into the report correctly. No ZilInventor equivalent found.

**Requirement framing:** the highest-value, lowest-risk items to close here are (1) a per-item unit-price field feeding a cost/quote total in the BOM CSV/export, and (2) a downstream QR-scan reconciliation flow (even a simple "scan → mark produced → track against BOM" web view) — both are plausible near-term additions since ZilInventor already generates the QR payload needed to drive them. Template/preset flexibility on the label PDF itself is lower priority (cosmetic, not a production-blocking gap).

## Drawings gap: ABF's fragile, model-mutating Exploded View vs. ZilInventor's parametric drawing system — where ZilInventor is structurally ahead

This is the second clear case of ZilInventor being ahead, and the gap is architectural, not incremental. ABF's only native drawing-adjacent feature is "Explode View" (Vietnamese: "Sơ Đồ Bung"), and it has a serious documented caveat: invoking it **converts the selected parts into a new separate Group and physically detaches them from the live parametric model** — a Ukrainian tutorial source states this explicitly ("breaks" the module) and recommends running it only on a duplicated scene or a copy of the file, never on the production model. Output is produced via SketchUp's generic "Export 2D Graphic" command (PDF demonstrated) — ABF has no dedicated drawing-export dialog of its own. There is no evidence of dimension annotations, section views, BOM tables on a drawing sheet, or multi-sheet drawing packages in core ABF. True dimensioned per-part drawings and hole maps exist only via a **separate paid third-party plugin** ("OK Hole Map" / "OK Exploded View," ~199 ₴/month, not from the ABF vendor). Tellingly, the community consensus on the official SketchUp forum, and the presenter of the primary Ukrainian tutorial personally, is that real "working drawings" are built in SketchUp + LayOut, not via ABF — i.e., ABF's own user base doesn't trust its native drawing tool for production documentation.

ZilInventor's `.zidw` drawing subsystem (Sub-project 6 + F-series features) is, per the inventory, "comparably mature to Inventor's drawing module": orthographic/section/detail/broken views, auto-dimensioning, baseline/ordinate/angular dimensions, hole tables, center marks, material-colored section hatch, a live view-projection pipeline with regen-on-change, drawing templates, and PDF/SVG/PNG/DXF export — all non-destructive (the source model is never mutated to produce a drawing). This is not a feature-by-feature superset comparison; it is a different category of tool. ABF bolts a one-shot, destructive diagram generator onto a non-parametric modeler; ZilInventor has a genuine associative drawing environment.

One caveat from the inventory: several ZilInventor drawing sub-features (part/edge tagging + balloons, live-view autoregen, drawing templates, view alignment) are shipped on **unmerged feature branches**, not yet on local master, as of the inventory's snapshot — this doesn't change the structural verdict but means "shipped and available today" should be double-checked against current branch state before citing specifics in a spec document.

**Verdict: ZilInventor structurally ahead — no action needed to match ABF here; if anything, this comparison validates ZilInventor's drawing architecture as the better long-term bet.**
